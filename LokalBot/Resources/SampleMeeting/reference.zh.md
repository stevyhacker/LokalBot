# 示例：Orders API 的 delivery window

Reference transcript of the LokalBot sample meeting: what each synthetic voice was asked to say, with the time each turn starts in the recording. The people and the company are fictional.

**[00:00] Maya:** 这是 LokalBot 的示例会议。里面的声音是合成的，公司和人物也都是虚构的。

**[00:07] Maya:** 嗨，Daniel。能听清我说话吗？

**[00:10] Daniel:** 听得很清楚，Maya。不好意思晚了一分钟，我的构建刚才还在跑。

**[00:16] Maya:** 没关系。我们来把 Orders API 的 delivery window 定下来吧。

**[00:22] Daniel:** 好。先简单说下背景：客服希望客户看到的是一个 delivery window，比如下午两点到四点之间，而不是我们现在返回的单个 ETA 时间。

**[00:36] Maya:** 对。而且合作伙伴成功团队的 Priya 说，我们最大的三个合作伙伴也提了一样的需求。

**[00:43] Maya:** 所以上周定的方案是：用一个新的 delivery window 对象替换 ETA 字段，作为 API 的第三版发布。

**[00:53] Daniel:** 原来是这么计划的。这个时间窗口用两个时间戳表示，一个开始一个结束，都用 UTC。第三版我可以在十一月十八号之前做好。

**[01:05] Maya:** 好。目前的决定是：做第三版，用 delivery window 替换 ETA，目标是十一月十八号。

**[01:14] Daniel:** 性能上两种都没问题。我昨天测过，P95 延迟一直在一百八十毫秒左右。

**[01:21] Maya:** 很好。那移动端 App 呢？

**[01:24] Daniel:** Tomás 说移动团队可以放进四点二版本，但不能再早了。

**[01:30] Maya:** 可以。那测试呢？

**[01:32] Daniel:** Lena 会补上契约测试。schema 冻结以后，她需要两天。

**[01:37] Daniel:** 其实，在我们定下来之前，我昨晚把合作伙伴的集成都过了一遍。一共有四十二个合作伙伴在调订单接口，其中十九个用的是自动生成的客户端，只要缺了它们预期的字段就会报错。如果我们删掉 ETA，这十九个在上线当天就会挂掉。

**[01:58] Maya:** 四十二个里有十九个，差不多一半了。而且做第三版就意味着每一个合作伙伴都得迁移。

**[02:08] Daniel:** 没错。光是 Fernhill 迁到第二版就花了四个月。

**[02:12] Maya:** 那我们改一下决定。不做第三版。响应保持向后兼容：ETA 完全保持不变，delivery window 作为一个新的可选字段加进去。如果不知道时间窗口，就不返回这个字段。

**[02:30] Daniel:** 可选，未知的时候不返回，ETA 不变，我们继续用第二版。这样工作量也更小。我可以在十一月十一号上线，不用等到十八号。

**[02:41] Maya:** 太好了。那会议记录里写清楚：这个决定取代了我们一开始说的方案。响应保持向后兼容，delivery window 是可选的，我们十一月十一号上线。

**[02:53] Daniel:** 那我可以告诉 Lena，schema 已经冻结了吧？

**[02:57] Maya:** 对，去说吧。Priya 会给提出需求的那三个合作伙伴发邮件。Daniel，你能更新一下 API 规范和变更日志吗？

**[03:09] Daniel:** 可以，这两样我周五之前都搞定。

**[03:11] Daniel:** 还有一件事我们没想清楚：变更之前创建的订单，要不要回填 delivery window，还是只给新订单加？

**[03:21] Maya:** 嗯。回填的话，要对大约两百万个未完成的订单重新跑一遍估算程序。说实话，我不确定值不值得。

**[03:33] Daniel:** 我也说不准。这要看合作伙伴到底会不会去看旧订单。

**[03:39] Maya:** 这个先放一放吧。我去问问 Priya，合作伙伴的旧订单需不需要这个。

**[03:45] Daniel:** 好的。那回填这件事还没定。

**[03:49] Maya:** 对。谢谢你，Daniel。今天就到这儿。
