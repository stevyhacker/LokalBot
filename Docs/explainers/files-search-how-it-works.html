LokalBot · Files and screens

Search your folders by what is in them

Files brings DigUp's file search into Ask. You choose folders; LokalBot reads the pictures, screenshots, PDFs and documents in them on this Mac, and Ask, Quick Recall and the Ask assistant can then find a file by what it says or shows, not only by its name. The same image model also lets screen search find a captured screen by what it showed (page 5).

“the clause about pets in the lease” → the PDF, opened at page 4 “payment declined error” → the screenshot “a dog on the beach” → the photo “where they talk about sleep” → the podcast, playing at 12:34 “INV-2041” → the invoice, by its exact words
Taken from DigUp
  • The engine, DigUpKit, pinned by commit: crawler, skip rules, readers, index, search.
  • Its image sizing, ported to Swift: matches Pillow bit for bit.
  • Its ranking: meaning per modality plus exact words.
Added by LokalBot
  • An embedder that talks to LokalBot's own llama-server, not DigUp's llama.cpp build.
  • Ask, Quick Recall, the assistant's tool and [file:ID] citations.
  • Moments play in a LokalBot window; the assistant hears the matched 30 seconds.
  • Pauses for recordings, Low Power Mode and heat; Settings with a notice.
Left out for now
  • DigUp's own panel, hotkey, updater and model downloader.
  • Code search.
  • Search by meaning for external agents: the CLI and MCP search Files by words only.
Try it. Settings → Personal Context → Files → Search my files, then Add Folder… for Documents, Downloads or a photo folder; Settings shows each pass as it runs. In Ask, type what you are looking for: files follow meetings and screen moments, and Sources → Result type → Files shows only files. Quick Recall lists them under Files. Ask a question, and the assistant searches them too and cites the file it used.

Indexing

One indexing pass, step by step

A pass runs at launch, when the folder list changes, and five seconds after something in the folders changes. It reads only what is new or changed, and the image model loads only when there is something to read.

  1. 1

    Trigger launch · folders · FSEvents + 5 s

    Changes inside hidden folders are ignored. A burst of changes becomes one pass.

  2. 2

    Should it wait? checked before each batch

    A meeting is recording, Low Power Mode is on, or the Mac is hot (thermal state serious or critical). Then it waits, and starts again when that ends. On battery, a folder's first read waits for a charger; up to 50 new files are read anyway.

  3. 3

    Sync CPU · no model

    DigUp walks the folders and compares sizes and dates with the index: new and changed files are queued, moved files keep their vectors, deleted files and folders taken off the list leave the index.

    Nothing new? The pass ends here. An unchanged library never loads the image model.

  4. 4

    Prepare the model first time only

    Downloads the 555 MB projector (and the 310 MB text model, if search by meaning never ran), each checked against its pinned size and SHA-256.

  5. 5

    Start the media server ≈ 1 s · 873 MiB

    A llama-server on port 17876, held in memory for the pass.

  6. 6

    Read and embed CPU reads · GPU embeds

    Screenshots first, then pictures, PDFs, documents, recordings and video, newest first. While the GPU embeds one file, a CPU thread decodes, OCRs or extracts the next. Long PDFs get their first 30 pages now. While you use the Mac it rests twice as long as each batch took; two minutes idle, it runs flat out.

  7. 7

    Finish long files 30 pages · 40 chunks a step

    The rest of PDFs over 50 pages and of long documents, once everything else is searchable.

  8. 8

    Let go 2 min · 10 min

    The media server stops two minutes after the pass. Search vectors leave memory after ten minutes without a search.

  • Hidden files and folders, ~/Library, app bundles, Photos libraries.
  • Caches: CACHEDIR.TAG, node_modules, DerivedData, .noindex.
  • Inside code projects, everything but screenshots.
  • Folders that look like datasets (300+ machine-named media files).
  • iCloud files that are only in the cloud: never downloaded.
  • Pictures under 256 px, links, copy-protected audio.
Outages don't cost files. If the media server stops answering, DigUp ends the pass and keeps the files queued for the next one. Only a file that can't be read, like a broken picture, is marked failed, and it is read again when it changes.

Ranking

Each search scores every vector, then centres the scores within each modality, because text scores higher than pictures for the same topic. A file counts when it stands out by meaning (z ≥ 2) or holds at least half the query's words; exact words add a bonus, so invoice numbers and names win. On DigUp's evals this found the right file first 88% of the time, against 73% with reciprocal-rank fusion, the method LokalBot uses for screens today (synthetic eval; 86% against 82% on real files).

Privacy boundaries
  • Off until you turn it on after a notice; nothing is read until you choose a folder.
  • Reads only the listed folders; never changes, moves or uploads a file.
  • Turning Files off deletes the whole index at once.
  • A remote Think model sees file passages only when you ask with Files selected, and only at an origin you approved.
  • External agents (CLI, MCP) search Files by words only, and only while Files is ticked under Settings → Privacy → External agents.

Screens

Screens by what they show

With Text + visual context and search by meaning on, each retained screenshot also gets a vector of its picture, and screen search ranks text and picture vectors with the query's words the way DigUp ranks files.

Why pictures · your library, 13 October
Screen searchFirstTop 5
Picture vectors71 / 138107
Screen-text vectors5284
Shipped: words + text, rank fusion4476

505 real screens, queries written by a different model from the pixels (content in English and Serbian, appearance in English). Picture vectors won for every kind of query. Fusion scored below text alone because the OR-fallback word list weighed as much as meaning; the new ranking removes that. This exact combination has not been rerun on your library yet.

Compute and storage
  • ≈ 70 s of GPU a day for about 490 captures, in passes 15 minutes after new captures.
  • ≈ 21 MB of picture vectors for 14 days of captures (3 KB each).
  • Searching adds one dot product per retained screen; the query vector is the one the text server already made.
  • Starts only after your first search of screens by meaning, which is when the 555 MB projector downloads if Files hasn't already.
  • Waits while a meeting records, in Low Power Mode, and while the Mac is hot; paced while you work, and on battery only the newest 48 captures a pass.
Where it shows. Screen moments found by their picture appear in Ask and Quick Recall marked "Related by meaning", with their window title when they have no text. The assistant's search_screen uses the same ranking, so it can answer "the dashboard with the red chart" even when no word on screen says so.
