# Agent CLI & MCP

Part of the [development guide](../../DEVELOPMENT.md).

`lokalbot-cli` (ArgumentParser, embedded in `Contents/Helpers/`) gives coding agents read-only access to the meeting library via `list` / `get` / `search` / `actions` / `people` / `path`, to shared Personal Context via `personal-context`, and to the Files index via `search-files`, plus `ask` and `reply`, which answer a question or draft a reply to a message with the app's local model through the same `AskLibraryEngine` path as `ask_library` (the Raycast extension in `Distribution/raycast/` uses them), and to app settings and status via `config` / `status` / `open`. `actions` and `people` share the app's outcome projection, thread clustering, due-date resolution, and People rules (the CLI target compiles those model files). JSON by default, `--table` for humans. `list --include summary` (MCP: `list_meetings` with `include`) adds several meetings' summaries in one call; they share a 20,000-character budget (`SessionFormatter.listSummaryBudget`), split so short summaries stay whole, and a cut one carries `summary_truncated`. Settings → External Agents → Agent CLI (or `lokalbot-cli install-skill`) symlinks the binary to `~/.local/bin/lokalbot-cli` and the bundled skill to `~/.agents/skills/lokalbot-cli/`.

The same binary is an **MCP server**: `lokalbot-cli mcp` speaks MCP over stdio. Meeting tools are `list_meetings` / `get_meeting` / `search_meetings` / `ask_library` / `get_action_items` / `list_people` / `get_person`; people tools return names only, never attendee addresses. Independently gated screen tools are `search_screen` / `get_timeline` / `get_recent_activity` / `get_app_usage` / `get_screenshot_detail`; they use a query-only SQLite connection and return captured text/metadata, never decrypted pixels or file paths. `get_personal_context` (CLI: `personal-context`) returns Personal Context items the user shared, ranked for the agent's task. `search_agent_notes` (CLI: `search-notes <query> [--agent] [--limit] [--table]`) searches the saved coding-agent notes by words through `AgentNotesIndex`, with the app closed. `search_files` (CLI: `search-files <query> [--kind screenshot|image|pdf|doc|audio|video …] [--after YYYY-MM-DD] [--before YYYY-MM-DD] [--limit N]`, `FilesSearchTool` in `CLISupport/FilesAccess.swift`) is word search over the Files index: DigUp's keyword search of the text Files extracted from documents, PDF pages, screenshots and pictures, plus file names, opened from `files-index.noindex` without vectors, so it works with the app closed. Hits outside the folders in `control/files-access.json`, or no longer on disk, are dropped; each result has the path, kind, page or seconds, modified and EXIF capture dates, size, excerpt and the matched passage (cut at 1,500 characters). Recordings and video match only by name. Search by meaning stays in Ask, because it needs the app's embedding model. It returns `files_access_disabled` without the grant and `files_unavailable` while Files is off, has no folder, or has no index yet. `get_briefing` (CLI: `brief`, listed first, and named in the `initialize` result's `instructions`) is the start-of-session overview built by `Briefing` in CLISupport; `brief` renders it with `Briefing.Vocabulary.cli`, naming `lokalbot-cli` commands where `get_briefing` names MCP tools: a capability index that is shown even with every grant off (for Files it says only whether the grant is on and how many folders it covers), then shared Personal Context items, the user's open action items, work-memory projects and goals (each source kind needs its grant, unattributed entries are skipped, and everything waits while `.dream-revocation-pending.json` exists), coding-agent sessions from `coding_agent_bursts`, and a review timeline: days from `dreams/*.json`, then week and month lines from `dreams/rollups/`, clamped to the screen profile and capped at 12,000 characters. `DreamRollupService` writes those lines after each overnight review (at most three, at most once in 20 hours via `dreams/rollups/.last-generation`, and only while agents may read all retained screen history, the only scope whose briefing shows them); each records a SHA-256 stamp of its reviews' days and `generatedAt`, so a deleted or regenerated review makes it stale. Stale lines are never shown, and `DreamStore.invalidateReport` deletes them. The server reads stdin with `read(2)`, so a client that keeps stdin open gets each reply immediately. The screen marker stores one of three profiles: today, rolling seven days, or all retained history; every query is clamped and out-of-scope detail ids appear missing. LokalBot does not upload library content, but an external MCP client may transmit tool inputs and results under its own privacy terms.

All agent surfaces are **off by default**. Meeting tools require `control/agent-access-enabled`; screen-memory tools require the separate JSON `control/screen-memory-access-enabled` marker; personal context requires `control/personal-context-access-enabled` plus the app-written `control/personal-context.json`; `search_files` requires `control/files-access-enabled` plus `control/files-access.json`, the chosen folders, which `FilesAccessManager` writes only while the grant is on and Files is on with a folder; `search_agent_notes` requires `control/agent-notes-access-enabled` and finds notes only while `agent-notes.sqlite` exists; settings commands require `control/settings-control-enabled`. No marker grants another capability, and Agent Mode capabilities don't grant personal context or files. In the Mac app, Settings → External Agents shows the four read grants as one switch, **Allow external agents to read your LokalBot data**, with a box per kind (Meetings, Screen memory, What I shared about myself, Files). `AgentReadAccess` only writes and removes the per-kind markers: turning the switch on grants the ticked kinds (Meetings alone the first time), and turning it off removes every read marker and saves the boxes and the screen scope to `control/agent-read-choices.json`. The switch is on exactly while some kind is granted, so grants from the old per-kind toggles or from agent setup show as they are, nothing widens on upgrade, and Files starts off. The last ticked box can't be unticked. Access-off messages name that path (`AgentReadAccessCopy`), and `open settings filesAccess` (like `agentAccess`, `screenMemoryAccess`, `personalContextAccess`, and `settingsControlAccess`) opens Settings at that box. Settings access stays a separate switch. Empty markers written by older builds retain their prior unscoped authorization until the user chooses a profile; newly enabled access defaults to seven days.

**Settings and status.** `lokalbot-cli config schema|describe|search` read `SettingRegistry` (`CLISupport/SettingRegistry.swift`) without the app: every persisted `AppSettings` key with its Settings category, type, consent tier, and choice tokens (enums that store display strings or key codes map to stable tokens). `config list|get`, `status`, and `open settings [key]` ask the running app over a Unix socket, one JSON request per connection (`AppControlProtocol`, `AppControlServer`, `AppControlHandler`). The socket is `control/app.sock` (0600, in the 0700 control folder), or a per-user `/tmp` name when the root path exceeds `sun_path`; it exists only while `control/settings-control-enabled` is on, and the app checks the peer's uid and re-checks the marker on every request. When no app answers and none holds the library's `.instance.lock`, the CLI launches its own enclosing bundle with `open -g -j <app> --args --lokalbot-background-launch`; menu-bar-only installs then start silently, like a login launch. `SettingRegistryTests` fails when a stored key has no spec or a choice drifts from its enum. `config set|reset|import` send `settings.set`: `SettingChange.swift` parses typed values, maps tokens to stored values, and classifies each change as preference, narrowing, widening, or read-only; `SettingsChangeApplier` decodes the result with the real decoder (a rejected or adjusted value is an `invalid_value` error) and applies the couplings Settings enforces (tracking and capture mode, the dreaming start day). Requests apply all or nothing. A request with a widening change goes, whole, to `SettingsApprovals` and returns `needs_approval` with the request (`id`, `changes`, any retention review) in `details`; the app posts a notification through `RecordingNotifier` (or opens the `settings-approval` window when notifications are off), the menu bar's status block lists it with Review and its icon carries a dot, and the window's card applies it through `AppState.applyApprovedSettings`, which re-plans against current settings, applies a shorter retention policy only through the review the card showed, and asks for the permissions the Settings controls would. `settings.request` reports `pending`, `approved`, `denied`, or `expired` (5 minutes); the CLI's `--wait` polls it and exits 0, 3, 4, or 5. `secret.set` queues an API key the same way (`AppSecret`, held in memory until answered, written through `AgentSecretStore`), and `secret.clear` removes one directly. The couplings and permission prompts the Settings controls use live in `AppState+AgentSettings.swift` (`changeSettings`, `coupledSettings`, `requestPermissions(forChangeFrom:to:)`, `applyRetentionReview`), shared by the controls, the socket, and Undo. `AgentSettingsChanges` appends each applied change, with the caller (the peer pid from `LOCAL_PEERPID` and its nearest non-shell ancestor), to `diagnostics/settings-changes.jsonl` and backs the Undo list in Privacy. `status` also reports model readiness, onboarding, and waiting approvals. Agent-led setup ([AGENT_SETUP.md](../../AGENT_SETUP.md)): `setup start` is the one request that needs no grant. The CLI writes `control/setup-request.json` (`AgentSetup.Request`, five minutes, 0600), opens its own bundle with `--lokalbot-agent-setup` or posts the `me.dotenv.LokalBot.agent-setup-requested` distributed notification to a running copy, and polls `control/setup-answer.json`. `AgentSetupRequests` shows the request in the `agent-setup` window (instead of the onboarding wizard on a new install), and only Allow writes the markers. `setup start --meeting-library`, `--screen-memory`, and `--files` add a box each to that window (Let agents read your meetings, Let agents read screen memory, Let agents search your files), off unless the person ticks it. `setup.plan` returns `SetupPlan.keys` with current values and the preset `suggestedPreset` picks for this Mac's memory; the CLI's `setup apply` applies preferences directly and sends consent changes to one approval card. `models.*`, `permissions.*` (the table behind Memory Health), `app.launchAtLogin`, `app.restart`, `setup.finish`, and `doctor` live in `AppControlHandler+Setup.swift`; prompts, launch at login, and restarts are refused outside the interactive app. See [the design](../designs/cli-configuration-design-2026-10-17.md).
