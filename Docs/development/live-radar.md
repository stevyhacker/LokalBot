# Live Radar and Follow-through

Part of the [development guide](../../DEVELOPMENT.md).

Built during the Meta Global AI Developer Hackathon on top of v0.11.4; see [the hackathon write-up](../meta-hackathon/README.md). Live Radar, with its screen answers and live answers, and Follow-through have since moved from Meta's models to the Think model. Only fast live text still uses Meta's.

- **Live Radar's model:** `MeetingRadar` gets a Think engine per request from `ThinkExecution.makeTextEngine` (priority `.interactive`), so the backend, its origin approval, and the remote gate are Think's own. `ThinkChat` (`LokalBot/Engines/ThinkChat.swift`) turns the radar's chat messages into what a `TextEngine` takes: a pass is one schema-held reply (`structuredReply`, `MeetingRadar.passOptions`); a live-answer turn is one JSON tool call `{"call": {"tool": …, "arguments": …}}` held to a schema built from the function definitions (`toolCall`, `MeetingRadar.answerOptions`), with the tools described in the system prompt and earlier calls and results passed as context, as Ask's loop does. A reply that is not a call is asked for once more. The engines report no token use, so passes on Think carry no cost. Live Radar is offered only with `liveRadarEnabled` (off by default; settings saved before the switch existed default it to whether `https://api.meta.ai` was approved). In the UI-test host with `LOKALBOT_MUSE_UI_TEST` set, the radar keeps Meta's wire format (`MuseUITestTransport.radarCall`/`answerCall`) so the hosted film's scripted and live replies still apply.
- **Meta connection (fast live text; the film and the replays):** `MetaModelAPI` (`LokalBot/Engines/MetaModelAPI.swift`) holds Meta's OpenAI-compatible endpoint, the standard Muse models and prices, and `MuseChatClient`, a small `/chat/completions` client with function tools, strict JSON schema, `reasoning_effort`, and token use. In the app only fast live text reaches Meta; `MuseChatClient` serves the hosted film and the replay harnesses, and its reply and message shapes are what `ThinkChat` hands the radar and Follow-through loops. Requests share the origin's `RemoteInferenceGate` and the same-origin redirect rule. The key is the Keychain item `meta-model-api-key` (`lokalbot-cli secret set meta-model-api`), falling back to Think's key when Think points at `api.meta.ai`. Sending also needs `https://api.meta.ai` in `approvedRemoteInferenceOrigins`, set from Settings → Meetings → Meta Muse. Contributor models are left out on purpose.
- **Live Radar:** `MeetingRadar` reads `LiveMeetingTranscriber.lines` through `RadarLineFeed`, keeps its own copy of every line, and runs a pass at most every 20 seconds (sooner after 10 new lines). `MeetingRadarAnalyzer` builds the request: the new lines (labelled `L1`, `L2`, … for the whole recording), up to 24 earlier lines, items already found, and up to six passages from earlier meetings that `LibraryRadarEvidenceSource` finds with local keyword and semantic search. The reply must match a strict schema; each item must quote a new line (exact after normalization, or 80% of its words), and a contradiction must cite a passage (`E#`) or an earlier line (`L#`) it was shown. Everything else is dropped and counted as rejected. Results are saved to `radar.json` (`MeetingRadarRecord`) after each pass, with timing per pass (and tokens and cost where the model reports them). The pane sits between the live transcript and notes; the finished meeting's page shows a Live Radar section with Follow Through on the person's own commitments.
- **Fast live text:** with `museLiveTextEnabled` (off by default) and the api.meta.ai approval, `LiveMeetingTranscriber` runs `MuseLiveTextTrack` (`LokalBot/Services/MeetingRadar/MuseLiveText.swift`) for each tee file instead of chunked local ASR. Each track opens a realtime session (`wss://api.meta.ai/v1/asr/realtime`, `ENDPOINTING` mode, 16 kHz PCM; the key goes in the handshake frame), streams the growing CAF in 100 ms frames, and turns `speechComplete` into a `Line` timed from its `speechStart`, with the in-progress turn as `partials`. `MuseLiveTextPacer` starts a session at most three seconds behind the live edge and pads a stalled track with silence, because the server closes streams that fall below real time. A session that ran 30 s or more reconnects at once (the server caps sessions at 60 minutes); one that fails sooner backs off like a local chunk. Speakers stay per track. The radar sees `deliversTurns` and passes after each turn, at most every 3 s (`MeetingRadar.Timing.turnInterval`).
- **Turn-by-turn live text:** with `turnByTurnLiveTextEnabled` (off by default; Muse's fast live text takes precedence), `LiveMeetingTranscriber.runTurns` replaces the 4 to 12 second windows. Every 100 ms it reads the whole 256 ms chunks each tee file gained (`LiveMeetingAudioPreparationWorker.readChunks`), asks `SpeechActivity.liveProbability` for each chunk's speech probability, and feeds it to that track's `LiveTurnCutter`: a turn closes after two quiet chunks, after one once it is 4 s long, or at 15 s at the quietest point of its last 1.5 s. Closed turns wait in `pendingTurns` and are transcribed one at a time with the Transcribe model, each as its own file (`prepareSpan`); a failed one is retried with the windows' backoff and survives a pause. Between turns, while the last decode took 0.25 s or less and the model is on this Mac, the open turn is transcribed again every 2 s of audio and shown as a `partials` line, as Muse's are. `deliversTurns` is true, so the radar passes after each turn. Cursors, the cutter and the speech-detection state live in the track state, so pause and retry continue where they stopped. [Benchmarks/transcribe/LiveTurns](../../Benchmarks/transcribe/LiveTurns/README.md) has the measurements and the opt-in replay tests.
- **Floating panel:** `LiveRadarPanelController` (`LokalBot/Views/LiveRadar/LiveRadarFloatingPanel.swift`) owns a borderless, non-activating `NSPanel` at `.floating` level (`canJoinAllSpaces`, `fullScreenAuxiliary`) hosting `LiveRadarPanelView`: the header with counts, `MeetingRadar.spotlightID` (the newest item, or the question that just got a screen answer) as a large `RadarCard`, the rest as rows, and the last transcript lines. `AppState` shows it when a recording starts with Live Radar on (`liveRadarEnabled` and `liveRadarPanelEnabled`) and from `startLiveRadar(for:)`, and hides it when the recording stops. `sharingType` is `.none` unless `liveRadarPanelHiddenFromCapture` is off (always `.readOnly` in the UI-test host, so the film can see it). Its top-left corner is kept in `UserDefaults` (`liveRadarPanelOrigin`).
- **Screen answers:** with `museScreenAnswersEnabled` (off by default), each question a pass adds starts `MeetingRadar.answerFromScreen` beside the passes. `LibraryRadarScreenSource` runs `ActivityStore.searchOCR` (OR'd terms, captures before now, not LokalBot's windows) and decrypts each hit; `RadarScreenAnswers.crop` runs Vision `.accurate` text recognition on the decrypted image and keeps a band around the best-matching lines, as wide as the text in it (at most half the screen tall, JPEG, at most 1,600 px wide) plus that band's text in reading order. The text of up to three crops goes to the Think model (`RadarScreenAnswers.textMessages`) with a strict `{answer, image, quote}` schema; `RadarScreenAnswers.answer` keeps the reply only when the quote is in that crop's text. The hosted film and the replay send the crops themselves as `image_url` parts (`RadarScreenAnswers.messages`). The crop is saved as `radar-answers/<item>.jpg` and the answer as `RadarItem.screenAnswer`; the request is recorded in `MeetingRadarRecord.screenAnswerRequests`.
- **Live answers:** with `liveAnswersEnabled` (off by default), each question a pass adds also starts `MeetingRadar.answerLive`, which runs `LiveAnswerSession` (`LokalBot/Services/MeetingRadar/LiveAnswers.swift`) on the Think model (at most 6 model turns and 60 s). Memory comes first: `AppLiveAnswerEnvironment` puts the "Where it stands" notes of up to two tracked projects that share words with the question, active actions from the last 30 days, `PersonalContextBuilder` claims (when `askMemoryEnabled`), and work memory in the prompt as `[C1]`, `[C2]`, …. Then the model may call Ask's `search_meetings`, `get_meeting`, `get_action_items`, and `search_screen`, and `LiveAnswerTools` (`LiveAnswerTools.swift`) over `liveAnswerFolders`: `search_documents` (Spotlight with `mdfind -onlyin`, else file names ranked by the query's words, since Spotlight skips `~/Library`), `read_document` (PDFKit, `textutil`, and a small `.xlsx` reader, cut to the lines around the query), and in git repositories `search_code` (`git grep -F`), `read_file` (tracked files only), `recent_commits`, and `github` (`gh pr`/`gh issue`). Hidden paths, `node_modules`, and secret-looking names are never read, and commands time out after 8 s. Each tool result is labelled `[R#]`, and the `answer` tool must cite `C#`/`R#` ids with exact words; `LiveAnswerSession.ground` keeps a source only when its quote is in what it names (`RadarScreenAnswers.quoteIsOnScreen`) and titles it by the matching line (`path:line` with a GitHub permalink at the checked-out commit, a commit, `#123`). The answer is `RadarItem.answer` (`RadarAnswer`), the card shows `MeetingRadar.answerSteps` while it works, and the request is recorded in `MeetingRadarRecord.answerRequests`.
- **Follow-through:** `FollowThroughSession` runs a tool loop on the Think model (at most 10 model turns): `AppState.startFollowThrough` asks `ThinkExecution.makeTextEngine` for an engine at each turn (priority `.interactive`), so the backend, its origin approval, and the remote gate are Think's own, and `ThinkChat.toolCall` turns the turn into one JSON tool call (`FollowThroughSession.turnOptions`), as for live answers. The engines report no token use, so a run carries no cost. In the UI-test host with `LOKALBOT_MUSE_UI_TEST` set, it keeps Meta's wire format (`MuseUITestTransport.followThroughCall`) for the hosted film. Read tools are Ask's `search_meetings`, `get_meeting`, and `get_action_items`; screen search is excluded because it has its own grant. Proposal tools (`draft_email`, `propose_meeting`, `hand_off_to_coding_agent`, `mark_action_done`) only create a `FollowThroughProposal`; the loop waits for the person to approve, edit, or decline it in `FollowThroughSheet`, and returns what happened to the model. `AppFollowThroughEnvironment` carries out approved steps: a `mailto:` draft (also saved as the meeting's `follow-up-draft.json`), an `.ics` invitation opened in Calendar, a prompt filled into Claude Code or Codex through `ActionAgentHandoff`, or Mark Done. Names are resolved to calendar addresses on this Mac and addresses never go into a model message. Menus on action rows offer **Follow Through…**.
- **Replays:** `--radar-replay` and `--follow-through-replay` run the same request, grounding, and loop code against a fixture on Meta's models, with `META_API_KEY` from the environment; see [Benchmarks/think/MuseRadar](../../Benchmarks/think/MuseRadar/README.md).
