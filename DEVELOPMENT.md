## Build workflows

Build with Xcode 26.4 or newer (Swift 6.3 and the Metal toolchain), as required by the pinned MLX package. The app deployment target remains macOS 15.

The Xcode project is generated from `project.yml`. Regenerate it after editing project configuration or adding/removing source files:

```bash
xcodegen generate
```

Use the **LokalBot Dev** scheme for local development. Build it with:

```bash
xcodebuild -project LokalBot.xcodeproj -scheme 'LokalBot Dev' -destination 'platform=macOS' build
```

The prod and Dev targets share sources, but have separate bundle identities (`me.dotenv.LokalBot` and `me.dotenv.LokalBot.dev`) and macOS permission grants. `LOKALBOT_DEV` disables Sparkle's launch path in every Dev configuration. The dedicated **LokalBot UI Test Host** also sets `LOKALBOT_UI_TEST_HOST` and removes the menu-bar extra for XCUITest. Unit tests use the **LokalBot** scheme; see [Testing](#testing).

Dev and UI Test Host also have separate Application Support roots and Keychain namespaces. Dev starts with its own library and downloaded models; it never imports the release library automatically. An embedded CLI resolves the enclosing app identity, including when invoked through a symlink. `LOKALBOT_STORAGE_ROOT` remains an explicit fixture/storage override.

A release-identity build run from Xcode build products (any path under `DerivedData/` or `Build/Products/`) uses `~/Library/Application Support/me.dotenv.LokalBot.local-build` and its own settings suite, and never runs the library migration, so it cannot write the installed app's library. Set `LOKALBOT_STORAGE_ROOT` to point it at another library deliberately. Only one GUI process may use a library at a time: it holds `.instance.lock` in the library root, and a second copy waits up to 10 seconds for a quitting holder, then activates the running copy and exits. Headless flags, unit tests, and UI tests do not take the lock.

App Sandbox is intentionally disabled because Core Audio process taps do not work in the sandbox. Distribution uses Developer ID signing and notarization. When the user requests reinstallation of the installed app, use `Scripts/reinstall-preserve-permissions.sh` to validate signing identity and update it in place.

Sharing with phones and tablets links the Rust crate `lokalbot-sync` (`LinuxWindows/crates/lokalbot-sync`) as the local Swift package `Vendor/lokalbot-sync` (product `LokalBotSync`). Xcode resolves packages before any build phase runs, so build it before `xcodegen generate` and the first `xcodebuild`:

```bash
Scripts/build-sync-xcframework.sh
```

It needs `rustup` and `cargo` (https://rustup.rs); it installs the toolchain `LinuxWindows/rust-toolchain.toml` pins and the Apple targets it builds (arm64 macOS, iOS, and iOS Simulator), and does nothing while the crate, `Cargo.lock`, and the script are unchanged. The app target also runs it as a pre-build phase, so a crate change is picked up by the next build. Every workflow that builds the Mac app runs it first through `.github/actions/lokalbot-sync`.

The first build uses `Scripts/fetch-llama.sh` and `Scripts/fetch-sherpa.sh` to vendor native runtimes. Read their pins and the Swift package versions from the checked-in configuration rather than copying version numbers from prose. Preserve pins unless the requested work needs an update.

The `lokalbot-cli` target shares `LokalBot/CLISupport/` and selected model files by direct source inclusion. It is built before the app and embedded in `Contents/Helpers/`; it is not a shared framework. `project.yml` separately copies `.agents/skills/lokalbot-cli/SKILL.md` into `Contents/Resources/lokalbot-cli/`. Keep that skill self-contained unless its packaging is also updated. `Scripts/build-mcpb.sh` packages the helper for GUI MCP clients.

Unit tests are hosted inside the prod app binary and link `libllama` directly; `-bundle_loader` resolves host-defined symbols only. Generated `default.profraw` coverage files are gitignored and should not be committed. Signing keys and populated environment files must remain outside version control.

## Recording & meeting detection

- **Detection:** native meeting apps combine process audio signals with bounded start/stop policies. `MeetingDetector.knownApps` lists them. Zoom, Webex, Tencent Meeting, and VooV Meeting are dedicated conferencing apps whose audio starts a recording at once; Teams, Slack, FaceTime, Feishu, Lark, DingTalk, and WeCom also carry chat sounds and voice messages, so their audio must last `nativeAudioMinimumConfirmationDuration` unless a calendar event backs it. WeChat is deliberately not listed, because its voice messages would pass that gate. Call audio from helper processes counts when the helper sits in the host's bundle namespace, plus the three that do not: Feishu's `com.bytedance.lark.helper`, DingTalk's `com.alibaba.DingTalk-Helper`, and Webex's `Cisco-Systems.SparkHelper` (`MeetingDetector.foreignHelperHosts`). Browser automatic starts require supported Google Meet in-call controls across consecutive observations; calendar entries and arbitrary browser output never authorize a start. Once authorized, an unreadable document, missing/unsupported controls, or a missing browser host does not stop or trim capture. Only explicit leave/end evidence, continuously verified bound-call closure after grace, a verified call in another room, or user Stop ends that browser recording. Meet's post-call page counts as leave evidence by its Rejoin and Return to home screen actions, whatever its heading says. Closure checks inspect other browser windows so moving the tab does not itself end the call. The original call binding survives uncertainty; a replacement browser host must verify the same room before capture attaches. While the bound call is unverified, the detector also reads other rooms (only the active calendar event's room when it has one); a call there that passes the normal start gate ends the stale session without trimming it and starts its own. While the bound call still holds its window, the next calendar event on the same room link splits the recording, as it does for native apps; an event in another room means the call is running over. A manual Start joins the detector's session only while its call is verified, and never takes an unverified call's room. A persistent notice explains that recording continues and browser process audio can include other tabs. Call observation diagnostics stay separate from content boundaries. The live capture environment reads each running app's pid, bundle id, and name once per process (`RunningApplicationCache`) instead of through LaunchServices on every 2-second detector tick, and `AudioSourceMonitor` queries Core Audio's process list on a utility thread. When a calendar-backed call ends on its own, rejoining the same event records again right away; after the user presses Stop, automatic detection waits five minutes before recording that event again. The next calendar event in a continuing call is a new meeting and records automatically even after the user stopped the previous one.
- **Two synchronized tracks:** `mic.m4a` (AVAudioEngine) captures microphone input; `system.m4a` captures the selected application process through a Core Audio tap. Audio source is separate from speaker identity. The engine re-installs its tap on `AVAudioEngineConfigurationChange` (AirPods/USB switches no longer truncate the recording), drains the converter on stop (keeps trailing audio), recovers helper-process changes without ending the microphone track, and encodes AAC off the real-time IOProc thread. A microphone that cannot be rebuilt within its fast retries (about ten seconds) is retried every 30 seconds for the rest of the recording, like system audio, instead of staying silent.
- **Recording timeline:** new recordings use timing version 2 and one continuous origin for both tracks and preview files. Late attachment, recovered gaps, and sleep insert bounded silence, preserving playback/transcript alignment. Detector lifecycle IDs prevent an unrelated native meeting-end event from stopping a manual recording. Historical version-1 recordings retain their original interpretation; repairing them would require a coordinated audio, transcript, and speaker-evidence migration.
- **Recovery and health:** meeting-intent recording persists its requested app/room and keeps late attachment alive for the recording's lifetime (fast initial retries, then every 30 seconds). Verified detector events wake it immediately; microphone-only intent never acquires a system source. Generation checks reject delayed work after Stop. The one-second watchdog reports missing successful writes at a five-second threshold, treats flowing silence separately, and checks disk space every 15 seconds. Persistent warnings and the menu-bar indicator supplement the per-source status. A warning becomes a one-time notification only once it persists (`CaptureWarningNotifications`): missing audio after 15 s, lost call status after the detector's 120-second grace, disk and write failures at once; dropped buffers never notify. `recording-health.json` records state transitions, dropped buffers, attempts, last verified observation, and completion. Capture warnings remain visible beside completed transcripts and notes; fewer than five dropped buffers per source do not count as a capture issue. Both recorders hand tap buffers between the real-time thread and the writer queue through a lock-free ring (`RealtimeBufferRing`), so a buffer is dropped only when all of them are in use. Browser observation enables a browser's page accessibility once per process: `AXManualAccessibility` for Chromium, `AXEnhancedUserInterface` only for Firefox, nothing for Safari.
- **Independent audio persistence:** both recorders attempt PCM recovery independently of AAC writes. Each track has a growing 16 kHz mono CAF plus independently closed PCM checkpoints under `mic.live.recovery/` or `system.live.recovery/`. Checkpoints target two seconds at buffer boundaries, close and synchronize before a SHA-256/frame-offset manifest is atomically saved, and consume about 230 MB/hour per PCM copy per track. Recovery reconstructs contiguous verified audio, can read an unmanifested final chunk, and retains original chunks on any coverage uncertainty. It never replaces a longer verified reconstruction with a shorter one. Redundant copies are removed only after complete primary decoding and duration/coverage checks (100 ms encoder tolerance). Relaunch repairs existing media without authorizing new capture. This is tested process-crash recovery, not a power-loss durability guarantee.
- **Capture priority:** new post-meeting jobs wait while recording starts or runs; active work yields at track/model phase boundaries after saving completed work. Recording no longer prewarms inference models. An in-flight model call is not forcibly preempted. Optional live transcription retains its separate opt-in.
- **Finalization:** stopping preserves failed metadata/processing-queue writes for retry and surfaces the error. Quitting saves automatic processing intent durably for the next launch without starting inference; an unsaved finalization cancels quitting so the storage error can be resolved and Quit retried. Reconnecting a microphone rearms bounded recovery after its earlier attempts were exhausted.
- **Missing transcripts:** after launch recovery, finished recordings of at least 5 seconds with readable audio, no transcript, and no queued, parked, or running job are queued once with automatic processing settings. A merged meeting whose transcript has no segment in the span of a source of at least 30 seconds is re-transcribed once; `transcript-gap-repair.json` records the attempt.
- **Imported recordings:** dropping an audio or video file onto Meetings or the welcome card, or choosing Recording → Import Recording…, runs `MeetingImportService`. It mixes the file's enabled audio tracks to AAC beside the library, moves the result into a reserved meeting folder as `system.m4a`, and writes `meta.json` last, so a library scan never sees a half-made meeting. The meeting is dated from the container's creation date, else the earlier of the file's creation date and modification time minus its duration, and never ends in the future. It records `importedFileNames`, which a merge carries over from its sources so the merged meeting stays imported, and then takes the normal user-initiated pipeline path. With no microphone track, its speakers are diarized system speakers, remembered and matched like call participants, and screen context from its time span is not attached.
- **Recordings from paired devices:** a phone or tablet sends an ADTS AAC file over the companion session (`Companion/protocol/protocol.md`, `purpose: "upload"`). `lokalbot-sync` resumes partial files in `companion/uploads/` and checks the SHA-256, then `CompanionRecordingReceiver` calls `MeetingImportService.importDeviceRecording`. The meeting takes the device's id, so a resend finds it, and its audio is `mic.m4a`, because a phone's microphone is the person's own. `importedFileNames` keeps screen context away. The pipeline starts without opening anything, and the device deletes its copy once it hears `accepted`, so that answer waits until the meeting is stored.
- **Menu bar:** the status item opens a panel (`MenuBarExtra`, window style; `MenuBarView`), shaped like a system status menu: one status block, then rows, each with an icon. `MenuBarStatus` picks the block's one state, in this order: recording (red: timer, the meeting, whether the microphone and the call's audio are arriving, Stop and Open live notes; amber while a capture warning stands), a running dictation (what it is doing, with Stop or Cancel), needs attention (amber: microphone access, the latest error, a settings change waiting for approval, each with its fix), a calendar meeting starting within `MenuBarStatus.soonWindow` or under way and not recorded (teal: Join and Record; the same schedule and rule as Today, read through `UpcomingMeetingSchedule` only while the panel is open, and never without the Calendar setting and macOS access), day memory paused, a recording saved within `MenuBarStatus.justStoppedWindow` (its name, length and Open notes), or not recording. A recording or a dictation keeps the block when something else needs attention, so Stop is never hidden; those items are listed under it. The rows are Quick Recall, Start dictation (it stops or cancels a running dictation and waits while a meeting records), Copy last dictation (earlier ones in its context menu), the two latest meetings, the Autocomplete switch, Pause day memory, Open LokalBot, Settings… and Quit; Live Radar and Hand off this window appear when those features can be used. ⌘, and ⌘Q are bound in the panel as well as in the app menu. The status item's glyph (`MenuBarIcon`, template images) shows the recording dot and timer, the dictation states, dims while day memory is paused and carries a dot while something needs attention; `AppSceneState` publishes those two states so the item redraws only when its glyph changes. The clock, the calendar and the sound levels are read only while the panel's window is on screen (`WindowVisibilityReader`).
- **UI:** a live meeting opens with quick notes and an opt-in rolling transcript. A completed meeting opens as a workspace with synchronized playback, reviewable action items, decisions, summary, transcript evidence, export, and reprocessing controls.

## Transcription & speakers

Engines (Settings → Models; CoreML/MLX, in-process, Neural Engine/Metal):

| Engine | Coverage | Notes |
| --- | --- | --- |
| **IBM Granite Speech 4.1** | high-accuracy local ASR | optional |
| **IBM Granite Speech 5.0 2B** (Q8, ~3.12 GB) | English, French, German, Spanish, Portuguese, Japanese | optional; local llama.cpp, vocabulary hints and punctuated output; separate from 4.1 and the English-only 470M TurboCTC model |
| **Parakeet Ultra 0.6B** (CoreML, ~0.63 GB) | 25 European languages | fast multilingual option; separate from existing v2/v3 selections |
| **Parakeet TDT 0.6B v3** | 25 languages, up to ~190× realtime in local benchmarks | fastest local option |
| **Parakeet TDT 0.6B v2** | English only | slightly higher recall |
| **Qwen3-ASR 1.7B** (MLX, ~2.47 GB) | 52 languages/dialects | **recommended**; best Qwen accuracy tier for harder recordings |
| **Qwen3-ASR 0.6B** (MLX, ~0.7 GB) | global coverage | compact tier |
| **Whisper large-v3 turbo** (WhisperKit, ~1.6 GB) | 99 languages | word timestamps; wide-language fallback |
| **SenseVoice / GigaAM** (ONNX) | CJK/Cantonese/English, Russian | specialist coverage |
| **Transcription server** (`RemoteTranscriptionEngine`) | whatever the server's model covers | opt-in; OpenAI-style `/audio/transcriptions` (OpenAI, Groq, OpenRouter) or whisper.cpp `/inference` on another device. Packs VAD spans into clips (≤15 s, or ≤30 s for a diarized track), uploads 3 at a time, and attributes speakers word by word like Qwen3-ASR (`.alignedWords`). Servers in `wordTimingModels` (MAI-Transcribe-2, Gemini 3.5 Transcribe, and Whisper large-v3 turbo on OpenRouter) are asked for `verbose_json` with `timestamp_granularities[]=word`, and their word times replace the Qwen3 forced aligner, which is then neither downloaded nor run; an HTTP 400 to those fields falls back to `json` and the aligner for that origin and model until relaunch. Other servers use the aligner, falling back to speaker regions. Its origin needs its own audio approval (`approvedRemoteTranscriptionOrigins`); plain HTTP only on private networks and tailnets |
| **Cohere Transcribe** (2B) | 14 languages | legacy — hidden unless already installed (no language detection, timestamps, or diarization) |

For Ukrainian, choose **Whisper large-v3 turbo → Advanced → Language & vocabulary → Ukrainian**. The saved `uk` selection disables Whisper's automatic language detection. Multilingual Parakeet Ultra/v3 also accept `uk`, but FluidAudio's hint only constrains the Cyrillic script and cannot distinguish Ukrainian from Russian. Unsupported local models disable the option and reject a previously saved Ukrainian selection with an actionable error; switching models preserves the selection. A transcription server receives `language=uk`, with support determined by its model. Regression tests cover selection, settings upgrades and reloads, decoder options, request fields, and rejection before inference. Ukrainian audio accuracy still needs a real Ukrainian sample.

Models auto-download on first use (Hugging Face; the ONNX specialists fetch sherpa-onnx archives from GitHub) and are cached under Application Support. huggingface.co is blocked in mainland China, so Settings → Models → **Download models from** (`ModelDownloadSource`) can route pinned Hugging Face file downloads through HF-Mirror (hf-mirror.com, same paths) or ModelScope (modelscope.cn). `ModelDownloadRouting` rewrites only `huggingface.co/…/resolve/…` URLs at transport time; stored URLs, the Hugging Face API used by Browse Hugging Face, and GitHub archives are unchanged, so `ModelDownloadManager`'s pinning policy still applies. ModelScope tracks branches rather than Hugging Face revisions, so it is used only for files whose listed SHA-256 equals the pin; other files go to HF-Mirror, then Hugging Face. A mirror's file is accepted only after it matches the pinned size and SHA-256, otherwise the next source is tried, and callers verify it again as usual. ModelScope's `HEAD` returns no size, so its downloads use the single-stream path rather than ranged parts. The transcription language picker includes Serbian: Qwen3-ASR does not list it, but naming it explicitly lowered WER from 17.1% to 14.1% on 1.7B, where auto-detection reads it as Croatian ([Benchmarks/QwenSpanLength](Benchmarks/QwenSpanLength/results/2026-09-30/REPORT.md)).

- **Speaker attribution:** microphone speech is the user's (“Me”) while Settings → Summarization → Speaker names → **My microphone is me** is on (the default); the preference also normalizes old persisted track/diarization defaults when read. Turning it off, for shared-room microphones, keeps microphone voices unidentified until confirmed. Explicit corrections, voice profiles, overlapping speech, and suspected echo keep their own identity. Microphone text that mostly repeats simultaneous remote speech is treated as suspected echo for notes evidence: it is withheld from the model, cannot prove ownership, and cannot outvote the speaker's own identity. User confirmations and supported voice-profile evidence are separate from track origin. Cross-track loudness correlation marks possible echo without relying on identical ASR text; speech is retained unless the narrower waveform-and-text proof authorizes duplicate removal. Summaries and action ownership use the same normalized provenance. Calendar guests remain suggestions even when only one attendee is listed; attendance cannot identify a voice. A freeform alias “Me” becomes “You” only when its speaker identity is confirmed as the user.
- **Neural diarization:** Settings → Meetings → **Separate voices by speaker** partitions microphone and system audio before ASR. Fresh installs default to **Nemotron 3 (Preview)**, a post-recording model for up to eight speakers using FluidAudio 0.17.7's `offline` preset and the ANE-compatible v2 CoreML export. Existing selections are preserved; older saved settings without a model field keep Pyannote Community-1 (threshold 0.70, step ratio 0.15, min segment 0.3 s), which remains selectable. Overlapping voices remain unresolved. When turns cut the audio into regions, a region under one second that the engine rejects (Parakeet refuses audio under 0.3 s) is skipped instead of failing the track. Nemotron's approximately 200 MB CoreML download is pinned by revision and per-file SHA-256 under `Models/NemotronDiarization/` in app support. Preparation is coalesced across processing requests; model failures surface for retry instead of checkpointing generic-speaker success. Partial transcript keys include the backend/weight identity. See the [public AMI benchmark](Benchmarks/NemotronDiarization/results/2026-09-23/REPORT.md) and [integration notes](Benchmarks/NemotronDiarization/INTEGRATION.md).
- **Known-name vocabulary:** for prompt-capable engines (Whisper, Qwen3-ASR, Granite Speech 5.0), Settings → Models → Language & vocabulary → **Add names LokalBot already knows** (on by default) appends calendar attendee display names, speaker names applied in related meetings (same series or shared attendees), Dream projects the person pinned (unpinned model labels are left out, since they can echo earlier mishearings), projects tracked in Projects, and distinctive title terms after the manual vocabulary (`TranscriptionVocabulary`). Addresses and names derived from them, speaker evidence, and profiles are never read. Terms are saved per meeting in `transcription-vocabulary.json` so a crash resume reuses its track checkpoints; dictation uses recent attendee and pinned project names. A recording whose tracks contain no speech finishes with an empty transcript instead of failing, so it leaves the failed list and is not re-run at launch. Placeholder labels ("Them 6", "Speaker unclear") and the "· source 2" suffix meeting merges add to names are never fed to the recognizer, and department words in titles ("Product standup") are not terms. A prompt-capable model answers a near-silent span with the hint itself ("Mila Novak, Orion Launch, Acme." in 0.4 s); `TranscriptionPromptEcho` drops such rows in the Qwen engine and the track transcriber, and `TranscriptSanitizer` drops them again before notes, together with precisely timed rows of eight or more words at ten or more words per second.
- **Remote speaker names:** LokalBot does not read Google Meet participant names or speaking labels. Remote voices are named in the rename sheet from calendar guests and typed hints; attendance alone never names a voice. The retired Meet observer's leftover files are deleted by the hourly speaker-evidence cleanup, while names already applied to transcripts remain.
- **Audio clock:** the Core Audio callback copies only its host timestamp and validity with the existing pooled-buffer handoff. The writer records anchors after successful file writes, so microphone and system timing cannot bridge missing buffers, recovery padding, or invalid timestamps.
- **Review and meeting memory:** the rename sheet offers automatic provenance, ranked suggestions, supporting playback, dismissal, undo/reset, and resume. The encrypted identity journal is authoritative before public aliases are projected. Corrections win over stale results; retranscription remaps retained audio turns against an exact audio digest, including clean splits and rejection of conflicting merges. Existing summaries can be explicitly refreshed after a correction. Private evidence never enters `Transcript` or the CLI source graph.
- **Local voice profiles (always on):** processing always exposes Pyannote's `embedding256` chunk vectors, except for the sample meeting. With Nemotron selected, an additional Pyannote pass supplies compatible vectors, mapped to transcript speakers only by temporal coverage (95% for microphone chunks; 60% for call chunks, whose sentence pauses carry no other voice). Nemotron channel IDs and internal state never become identity embeddings. Existing profile fingerprints are retained after the runtime compatibility check described in the integration notes. Every name the user saves enrolls the voice when there is enough clean speech: at least three disjoint chunks totaling 15 seconds, which no other speaker overlaps. `MeetingSpeakerIdentityService.samePerson` adds it to the remembered person with that name when the voice agrees, else creates a distinct person. Microphone voices keep the per-chunk rules (one chunk per clean turn, every pair at least 0.75) and are only suggested. Call voices (`SpeakerVoiceMatcher.Call`) are codec-compressed, so single chunks disagree; up to 16 chunks are averaged into one voiceprint, a median chunk-to-average agreement below 0.75 marks a mixed label, and a profile keeps one average per meeting. A call voice is named automatically at 0.70 or more with a 0.15 lead over every remembered person with a different name, and suggested from 0.60. `SpeakerVoiceReplayTests` (opt-in, `LOKALBOT_SPEAKER_REPLAY_MANIFEST`) replays this on saved meetings; on seven real Google Meet standups, every automatic name agreed with the names saved there. Automatic names never train profiles. After launch and after each naming, `AppState.learnSpeakerVoices` analyzes the call track of meetings named before call voices were kept (once each, marked by `callVoicesAnalyzed`; only when the Pyannote model is installed, and never while recording or processing) and re-identifies meetings from the last 14 days with `nameAutomatically: false`: a saved transcript is never renamed in the background, because a new name invalidates its notes. Recognized voices become suggestions that the meeting offers through **Apply Names**. Profiles use bounded normalized vectors, exact model/preprocessing fingerprints, source contributions, revisions, and deletion tombstones. A profile database revision check rejects results computed before a rename, deletion, or enrollment change.
- **Storage and retention:** meeting-private AES-GCM identity journals live under `speaker-evidence/`; the same library root holds `speaker-profiles/profiles.sealed`. A serial store commits decisions, expires voice samples and suggestions independently of feature toggles, and preserves confirmed assignments. Source deletion revokes enrollments before deleting audio. Key/storage failures leave an advisory and never stop recording.

## Summarization & notes

- **Meeting boundaries:** the meeting actions menu exposes a range in original audio seconds. Rebuilding transcribes only that range; raw tracks remain playable. Only a confirmed call end can suggest an automatic boundary; user-reviewed ranges remain authoritative, and legacy ranges are not expanded silently. Meetings with saved audio beyond their boundary expose a review action using the existing rebuild path. Crossing old transcript spans are excluded until retranscription establishes their words. Reviewing a boundary clears the meeting's semantic vectors for re-embedding without writing a deletion tombstone; launch clears tombstones left on live meetings by earlier versions so keyword and semantic search cover them again.
- **Summary recovery:** old source-less rejection checkpoints receive a fresh scan with accepted evidence retained. New invalid source IDs or stalled generation produce an explicit persisted provider failure; identical retries do not repeat requests. Changing the provider/model invalidates that checkpoint. Parts are planned beside a full output reservation; a continuation page's ledger and recovery text shrink that output (down to the structured-output minimum), then keep only the newest ledger records.

- **Backends** (Settings → Models): **Built-in** (included localhost llama.cpp runtime; choose/download a GGUF model) · **Apple Intelligence** (FoundationModels, macOS 26+, gated so the app still builds/launches on 15.0) · **Ollama** · **any OpenAI-compatible server** (LM Studio, vllm-mlx, …) · **your ChatGPT or Claude plan** (no API key). Non-loopback endpoints require explicit origin approval before context is sent; each plan has its own approval entry (`chatgpt-plan://api.openai.com`, `claude-plan://api.anthropic.com`) that an API-server approval never covers.
- **Subscription plans** (`LokalBot/Engines/Subscription/`): the **ChatGPT plan** follows OpenAI's Sign in with ChatGPT for open-source apps. `ChatGPTPlanAccount` registers on first sign-in with `dynamic_agent_client`, receives the issued client id on the `127.0.0.1` loopback redirect (`LoopbackRedirectListener`), verifies the ID token against OpenAI's published keys, and keeps the registration, a random host id, and the session tokens in the Keychain, refreshing one rotating token at a time. `ChatGPTPlanEngine` calls the public Responses API with `store: false` and `stream: true`, sends `instructions` instead of a system message, and never sends temperature or output caps. The **Claude plan** runs the user's own signed-in Claude Code (`ClaudeCodeCLI`, `ClaudePlanEngine`): `claude -p` with `--no-session-persistence`, `--safe-mode`, no tools, MCP servers, or setting sources, the system prompt in a private temporary file, and content on stdin. Never pass `--bare` (it ignores the subscription sign-in) or read Claude Code's credentials; Anthropic's terms require the unmodified binary and Anthropic's own sign-in. Plan usage-limit errors stop the request without a replay or a fallback to another provider. Agent Mode runs on the ChatGPT plan through `ChatGPTPlanRelay`: each task starts a relay on `127.0.0.1` with a random key, and pi's provider speaks the Responses API to it (`LOKALBOT_LLM_API=openai-responses`, a reasoning model so instructions go out as a developer message, no output cap). The relay accepts only `POST /v1/responses` with that key, removes the fields the plan route rejects, forces `store: false` and `stream: true`, adds the current access token (refreshing once on a 401), and streams OpenAI's reply back. Plan limits and eligibility errors carry `X-Should-Retry: false`, so pi doesn't retry them. The plan's own approval is checked when a task starts and before each message. Agent Mode reports the Claude plan as unsupported.
- **Output:** `summary.md` with TL;DR / Key points / Decisions / Action items / Open questions. Long meetings are extracted in parts with no separate combining pass; the TL;DR takes every part's first takeaway, then every part's second, so its first bullets span the whole meeting. `<think>` reasoning blocks are stripped.
- **Outcomes:** `MeetingNotesGenerator` projects decisions and action items into the local outcome index while `MeetingOutcomeStore` keeps user status changes separate from generated source material. The meeting workspace and Today can therefore mark, reassign, or open work in Agent Mode without rewriting the transcript. A correction to an action's owner, text, or due date re-renders the summary's action list and keeps the rest, whose lines are claims attributed to the speaker who said them. Older summaries without saved claims (`summary-claims.json`) can name the old owner in free prose, so an owner or text correction there still asks for a refresh. Action items list the user's work first: their own commitments and requests they answered in the next turn, then unclear-owner actions spoken on the microphone, then every other action by importance. Saved outcomes keep every validated action; views that show a short list cap only their own presentation.
- **Handing an action to a coding agent** (`LokalBot/Support/ActionAgentHandoff.swift`): every action menu (the meeting page, Actions, and Today) offers **Open in Claude Code** and **Open in Codex** after **Open in Agent**, each only while something on the Mac handles its link. A desktop app wins over a terminal. Claude Code opens in the Claude app's Code tab (`claude://code/new?q=`) when the app is installed, and otherwise through Claude Code's own `claude-cli://open?q=` link, a new window of the terminal it last ran in; Claude Code registers that handler after the first prompt of an interactive session. Codex opens in the Codex desktop app through `codex://new?prompt=`. The Codex CLI has no documented way to fill a prompt without sending it, so it has no fallback. The LaunchServices lookup is cached for a minute because workspace menus rebuild on every playback update. The prompt names the action's text, owner, due date, and status, the meeting's title, start time, and short ID, the transcript time of the first citation, and the absolute paths of whichever of `summary.md`, `notes.md`, and `transcript.md` exist. A thread lists up to five of its meetings, newest first, and drops older ones to stay under Claude Code's 5,000-character link limit. Neither link sets a working folder, so the agent never starts inside the library, and neither sends anything: the prompt waits in the agent's input box. `ActionAgentHandoffTests` covers detection, links, prompts, and limits.
- **Action ownership:** who owns a task is read from the voice that said it, not from the model's `owner` field or its quote (`ActionOwnership`, `SpokenUndertaking`). The cited row's speaker owns the task when that speaker's own words around the cited rows undertake it — "I'll", "I will", "I have to", "I need to", "I can", "let me", "I have some comments to resolve" — wherever they sit in the sentence ("the extraction PR is something I I have to update"), with repeated or stumbled words collapsed and a sentence followed across the rows the diarizer cut it into. A condition or hedge ("if approved, I'll…", "maybe I'll…") changes when, not whose. Ownership is refused only on a contradiction: a negation, a question (direct, or "I'm wondering if I should…"), reported speech ("I said I'll…"), work handed to someone else ("I'll need you to…"), or a remark about the conversation ("I'll be honest", "let me share my screen"). When the same speaker also hands out work in the same breath ("I'll write the notes and Dana will handle the rollout"), the task must read more like the speaker's own clause than the other person's, or it stays unclear; a passive ("that can be simplified") and an embedded question ("what do we need to change") name no rival. Two people undertaking something in the cited rows need the model's quote to choose. A bare acceptance ("I can do that", "I'll take it") in the next turn takes on what the row before asked. The model's quote only chooses among undertakings; the saved quote is always the sentence as transcribed. Languages the wording checks cannot read (`SummaryLanguage.isMostlyEnglish` samples the whole meeting, so a foreign-sounding opening cannot switch them off) fall back to the cited voice plus the model's claim. A claimed commitment with no undertaking in or around the cited rows, or only negated and questioned ones, is not a task; a stray "not" or "?" elsewhere in the row decides nothing. When no task cites a row whose wording reads like the user's own undertaking, notes ask the model once more about that row; a complete answer without a task is final. A task that merely repeats its cited words merges into the task written from them. `ActionOwnershipAuditTests` (opt-in, `LOKALBOT_OWNERSHIP_AUDIT=<folder of copied meeting folders>`) replays every saved action of a library copy through the current rules and reports what would change, with and without the model's claim.
- **Action threads:** membership uses canonical immutable source text and compatible source owners, never fuzzy similarity or editable corrections. Corrections retain membership; mixed completion remains visible. A meeting-level toggle writes only its own overlay; a multi-meeting toggle requires native confirmation and rejects stale thread snapshots. Ask includes all statuses by default and supports explicit active/open/deferred/done filters with per-source status for mixed threads.
- **Thread corrections:** each corrected field keeps its own revision time, so completing an older source cannot replace newer wording, ownership, or deadlines. Sources can be kept separate and allowed to match again without changing generated outcomes. Clustering indexes canonical text and owner within the 30-day window; bulk edits notify dependent products once.
- **Meeting context:** notes receive a source-labeled secondary block (`MeetingGenerationContext`) with the calendar title and invited names, titles of documents on screen during the call (`MeetingScreenContext.materialTitles`, never captured text), and, when Settings → Meetings → Calendar → **Use invitation agendas** is on (off by default), the invitation agenda sanitized by `CalendarAgenda` and saved as `calendarAgenda` in `meta.json`. The block instructs the model never to derive decisions, actions, owners, or claims from it. Summarization → the two **Give notes…** toggles control calendar and screen titles.
- **Due dates:** `ActionDueResolver` deterministically resolves ISO dates, weekdays, day/week/month/quarter ranges, relative offsets, and month-day phrases (English and common Serbian forms) against the meeting date, or the correction date for user edits. Ranges resolve to their last working day; unsupported phrases stay unresolved. Labels keep the phrase beside the date, and Today's Needs Attention orders overdue then due-within-a-week threads first (`ActionAttentionOrder`).
- **Completion hints:** `ActionCompletionDetector` searches retained screen text captured after an open action was last mentioned for two of its distinctive words plus a verb-appropriate completion phrase (message sent, merged, submitted, event created, approved). Matches show **Looks done?** with Mark Done, View, and Not Yet; status never changes without confirmation, and dismissed captures are remembered in user defaults. Settings → Screen & Activity → **Suggest actions that look done**.
- **Follow-ups:** the meeting actions menu, a person's page, and Quick Recall's "Draft follow-up for latest meeting" command open a follow-up sheet that starts from `FollowUpDraft.seeded` and can be rewritten by the on-device Think model (`FollowUpDraftGenerator`) from the recap, decisions, open actions, open questions, and invited names. It is copied or saved with the meeting, never sent; remote Think is refused.
- **Templates & language:** pick a notes template (Meeting / Lecture / Study guide / Podcast / Free-form) and a summary language (auto-detected via `NLLanguageRecognizer`, with Simplified / Traditional / Cantonese handling). Prompt budgeting (`TokenCountEstimator`, `PromptContextSanitizer`) keeps prompts within the model's context.
- **Notes context allowance:** for an approved OpenRouter origin, `OpenRouterModelCatalog` reads the selected model's `/models/<id>/endpoints` list (model id only, no API key) and `MeetingSummaryGenerator.contextTokenLimit` uses the smallest `context_length` or `max_prompt_tokens` across its endpoints. A failed lookup reuses the last published window from preferences, then `verifiedOpenRouterContextTokens` for the models the nightly drift job records (GLM-5.3, GLM-5.3 Flash, Qwen3.8 Flash), then 16K, which unknown external servers always get. Other OpenAI-compatible servers are asked for the window by `ServerContextWindowCatalog`, at most daily, with the configured API key: the model list's `max_model_len` (vLLM), `context_window` (Groq), `context_length` (Together, DeepInfra, Fireworks) or `max_context_length` (Mistral), and, for servers on this Mac, llama-server's `/props` slot window or LM Studio's loaded window. A reported window wins, even below 16K, and the last answer is kept in preferences. Cerebras and OpenAI publish no window through their APIs, so `MeetingSummaryGenerator.documentedContextTokens` uses their documentation: Cerebras's free-tier windows (Qwen3.8 27B 64K, gpt-oss-120b 65K) and OpenAI's by family at the smallest variant (GPT-4.1 1M; GPT-5, GPT-4o, GPT-4 Turbo and the o-series 128K). Each provider's window then sets its part size, below. Ollama requests ask for that 16K window with `num_ctx`, since Ollama's own default is smaller and drops the start of longer prompts; zero-reasoning requests also send `think: false`, and a reply cut off by its output limit (`done_reason: length`) is reported as truncated. Without a native tokenizer, UTF-8 bytes remain the hard input bound. Parts target 6,000 estimated tokens (about 18 KB) below a 64K window, 16,000 from 64K, and 24,000 from 128K (`MeetingSummaryGenerator.notesPartTokens`), so a 20-minute meeting on Cerebras Qwen is two requests instead of four. The steps keep a window that drifts between lookups from re-planning a meeting. A larger part gets proportionally more output (up to 16,384 tokens) and more notes and actions per request, and the job budget counts it as that many standard parts. Each part's schema lists its source IDs as enums three times, so hosted servers also bound part size by their limit on schema enum values (`TextEngine.structuredOutputEnumLimit`): Cerebras rejects more than 500, OpenAI documents 1,000, and OpenRouter and other hosted servers get 500; servers on this Mac compile the schema to a grammar and have none. A 20-minute meeting is therefore one request on OpenAI and two on Cerebras or OpenRouter. Changing the parts planned for a meeting discards its incomplete notes checkpoint.
- **Notes recovery:** a part continues only from records it already accepted; a page cut off before any record, for example because reasoning used the whole output, is scanned again rather than asked to "continue" from an empty list. Two answers in a row with no new records stop the part so automatic runs do not cycle; **Summarize again** clears that stop and scans the part once more. On Automatic reasoning, a task tuned for no reasoning sends Off to a model that reasons by default and can switch it off (Cerebras Qwen, OpenAI GPT-5.2 and later); other models keep their server default.
- **Pipeline:** runs automatically when a recording stops (configurable); serial queue with per-meeting status in the UI, plus a Process menu for manual re-runs.

## Built-in LLM runtime — llama.cpp & model catalog

- `LlamaServer` copies the vendored `llama-server` out of Resources into Application Support on first run (never executes from inside the bundle), spawns it (`-ngl 99 --jinja`, port 17872), health-checks `/health`, restarts on model switch, and terminates on quit. Each bundled version gets its own `llama-cpp/<sha256>/` folder (sherpa-onnx likewise). A running app holds a shared lock (`.claim-<sha256>.lock`) on every version it uses until it quits, and each install removes the versions that no app claims and no process runs from, along with the flat layout older releases installed.
- **Ports:** the release app's servers listen on main 17872, embeddings 17873, cotyping fallback 17874, Granite ASR 17875 and the Files media embedder 17876; the CLI and MCP `ask_library` connect to 17872. Release-identity builds run from Xcode share them. Every other copy gets its own block (`LocalRuntimeOwner`, `LlamaServerRole`): LokalBot Dev 17882–17886, the UI Test Host 17892–17896, and the unit-test host 17902–17906. Binaries, PID markers and bearer tokens live in the identity's Application Support folder; the unit-test host carries the release bundle id, so it uses `me.dotenv.LokalBot.unit-tests` instead. Residency ids and Resource Monitor labels name the role (`llama-server:main`, `:embedder`, `:cotyping`, `:granite-asr`, `:media-embedder`), not the port.
- **Orphaned helpers:** when a server's port is held by a LokalBot llama-server whose app has exited (its parent is launchd, it runs from a `me.dotenv.LokalBot*/llama-cpp/` runtime, and no PID marker there names a live owner), `LlamaServer.start` stops it and logs one line instead of failing with "port … is already in use". A helper still owned by a running app is never touched. To check by hand: `lsof -nP -iTCP:17873 -sTCP:LISTEN`, then the listener's parent (`ps -o ppid= -p <pid>`) and executable path.
- **Inference broker:** the three shared llama-servers — main (17872), embeddings (17873), cotyping fallback (17874) — are lease-managed by `InferenceBroker`: consumers take per-request leases, a server with no active leases unloads after a short linger, and loaded models sit under a RAM residency budget with LRU eviction. Settings → Diagnostics shows a live **resource monitor** of what's loaded and which lease is pinning it. The MLX speech engines (Qwen3-ASR, its forced aligner, Granite Turbo) idle-unload after two minutes, call the package's own `unload()` where it has one, and return MLX's GPU buffer pool (`MLXMemoryRelease`), which otherwise stayed allocated (4.3 GB after one meeting).
- **Model catalog** (Settings → Models) — download / cancel / delete with progress, radio-select the active model. Qwen "thinking" is disabled for summaries via `chat_template_kwargs`. The Models tab also manages the dedicated cotyping model, the embedding model, and the **Kokoro** TTS voice (sherpa-onnx; downloads once, then reads summaries and chat answers aloud offline).

## Search & player

- **Index:** SQLite + FTS5 (`lokalbotv3.sqlite` — system SQLite, no dependency) over titles, transcript segments, summaries, the user's `notes.md`, current outcomes (decisions, actions with saved text/owner/due corrections, and open questions), and OCR'd screen text. Ask's result types include Notes and Outcomes; a one-time `search-notes-outcomes-v1` migration reindexes older libraries, and note or outcome edits enqueue a reindex. Notes are also embedded for search by meaning. Segment rows carry their audio timestamp; incremental re-index by file mtime on launch and after each pipeline run. The `unicode61` tokenizer indexes an unbroken run of Chinese, Japanese, or Korean text as one token, so FTS5 alone matched a CJK word only at the start of a phrase. `CJKSearch` (in `CLISupport/`, shared with `lokalbot-cli`) therefore matches queries containing CJK text by `LIKE` substring on the stored text, in meeting search, the Meetings filter, screen search, and the MCP screen reader. Relaxed (OR) searches split a spaceless question into at most eight two-character pieces and rank by how many matched. A query without CJK text that FTS finds nowhere falls back to the same substring match, but only in rows containing CJK text, so a Latin word glued to Chinese ("比如logo再大") is found and English rows never match by substring.
- **Semantic search:** transcript/summary chunks and retained screen OCR are embedded with EmbeddingGemma 2 GGUF (`Q8_0`, approximately 0.31 GB, 768-dimensional vectors) on a second llama-server instance (port 17873, `--embeddings -b 2048 -ub 2048`). The GGUF carries the model's mean pooling and projection, so the server sets no pooling flag; as a bidirectional encoder it needs each input in one micro-batch, hence the 2,048-token batch. Queries use the checkpoint's `task: search result | query: ` prompt and documents `title: none | text: `, with prompt caching off. Vectors live in SQLite with an index-version marker covering the model, pooling, prompts, and chunking. Queries use brute-force cosine similarity. Screen OCR is embedded only after a library first searches screens by meaning: that search starts a backfill, later captures schedule one batched pass 15 minutes on, launch resumes rows left behind, and a failed pass retries after 1 minute, doubling up to 30 minutes, until it succeeds. Screen results rank the way DigUp ranks files (`ScreenSearchRanking`, shared by Ask, Quick Recall and the assistant's `search_screen` through `ScreenSearch`): every screen vector, text and picture, is scored against the query, centred per kind (text scores higher than pictures for the same topic) and put on one z scale over the whole library, so a date or app filter never moves the scale. A capture qualifies by standing out (z ≥ 2) or by holding at least half of the query's words; its score is the z plus a word bonus that grows with that share, and lookups made only of codes weigh words double. This replaced reciprocal-rank fusion, which gave the OR-fallback keyword list the same weight as meaning and pulled the right screen down on descriptive queries ([13 October report](Benchmarks/EmbeddingGemma2/2026-10-13-screen-images/REPORT.md)). With no screen vectors yet the keyword results stay as they are. With Text + visual context, `ScreenImageEmbeddings` gives each retained screenshot a picture vector: the pixels are decrypted in memory, sized for a 280-token budget (`FileImageSizing`) and embedded on the Files media embedder (17876), newest first, in batched passes like the text backfill (15 minutes after new captures, at launch, with backoff), paused while a meeting records, in Low Power Mode or when hot, and only once screens were searched by meaning, which is also when the projector downloads. Passes are paced like Files' (`IndexPacing`), and on battery a pass stops after the newest 48 captures (`batteryLimit`), so the first pass over a library waits for a charger. A picture vector is deleted whenever its pixels are: `ActivityStore.clearScreenshotPath` (retention) deletes it before clearing the path, and deleting a capture deletes it with the row.
- **Files** (Settings → Files, `LokalBot/Services/FileSearch/`): the folders a person chooses are searched by what is in them with DigUp's engine. `DigUpKit` ([ARahim3/DigUp](https://github.com/ARahim3/DigUp), MIT; pinned by revision through the [stevyhacker/DigUp](https://github.com/stevyhacker/DigUp) fork in `project.yml`) crawls and reads them and keeps the index in `files-index.noindex` in the library; LokalBot uses none of DigUp's UI, llama.cpp build or helper processes. `FileMediaEmbedder` implements DigUp's synchronous `Embedder` over HTTP to the `media-embedder` llama-server role (17876): the text GGUF plus `mmproj-embeddinggemma-2-Q8_0.gguf` (555 MB, pinned like the text model and downloaded only when Files is on), started with `--image-min-tokens 1 --image-max-tokens 1120`. Images are resized for their token budget in the app (`FileImageSizing`, a port of DigUp's `ImageSizing` that matches Pillow bit for bit) and sent as PNG content parts; audio goes as `input_audio` WAV parts. That path reproduces DigUp's reference vectors ([report](Benchmarks/EmbeddingGemma2/2026-10-30-media-embedder/REPORT.md)), and the text-only embedder makes the same query vectors, so searches never load the projector. A server that cannot answer throws `WorkerError`, so DigUp stops the pass and keeps files pending; any other error would mark the batch failed for good. DigUp's text recognition (the words in screenshots and scanned PDF pages, and the speed check) runs on `TextRecognitionQueue` like the app's other Vision text requests: `FileTextRecognition` sets DigUpKit's `TextRecognition.reader`, and a request waits at most 20 s. With no answer the file stays pending, or a long PDF keeps its place, the pass goes on with the next file, and a later pass reads it (`testAPassFinishesWithoutTextRecognitionThatNeverAnswers`); before, one request that never returned held the pass and its model until the app quit. `FileSearchService` runs passes at launch, when the folders change, and five seconds after FSEvents report a change. Each pass syncs first and starts the media embedder only when files are new or changed, stops at the next file while a meeting records, in Low Power Mode or at a serious thermal state, and releases the server two minutes after the pass. Big reads are paced: while the person is at the Mac (input in the last two minutes, from `CGEventSource`), `FileIndexPacer` rests between DigUp's jobs for twice as long as each job took (at most 20 s), so indexing gets about a third of the time; with no input it runs at full speed. The next job is decoded ahead during the rest. On battery, unless **Read big folders on battery** (`fileSearchReadsOnBattery`, off by default) is on, a pass reads only the files its sync just found, if they are 50 or fewer (`newFilesLimit`, as DigUp's helper does), and leaves the rest of a folder's first pass and of long files for a charger (`State.waitingForPower`); IOKit's limited-power notification (`.powerSourceDidChange`) resumes it. Until a folder is chosen, Settings offers Documents, Desktop and Downloads as one-click choices (`FileSearchService.suggestedFolders`), with symbols and catalog names rather than Finder's icon and display name, which would read inside those TCC-protected folders and prompt before the person picks one; picking one opens the same sheet, and macOS asks for access when the count opens it (a declined folder is reported as `unreadable`). Before a folder is added, `FileFolderAddSheet` shows what it holds, how long its first read takes on this Mac, how much room its index will take, and any model download still to come: DigUp's `Crawler` and `Estimator` read metadata only, with the costs indexing has measured here (`costs.json` in the index folder) or DigUp's M4 Pro costs scaled by its one-second speed check, run once. The index size uses per-item bytes measured on a real DigUp index (`FileIndexSize`: about 2.7 KB a picture, 6.7 KB a screenshot, 7.7 KB a PDF page, 8.7 KB per 2 KB of document, 2 KB per 25 s of sound or video frame); `FileIndexSizeTests` indexes a mixed folder and holds the projection within 20% of what DigUp writes (it came within 1% on 31 October). Indexing and search use separate connections on their own serial queues (WAL). Recordings and video are read too (DigUp's 30-second sound windows every 25 s, and a frame per shot at most every 3 s) unless **Include recordings and video** is off, which excludes them by extension; a moment opens in an `AVPlayerView` window at its time, and for the assistant `FileMomentTranscriber` exports that 30-second window to M4A and transcribes it with the configured engine, only when `ModelReadinessSnapshot` says the model is on disk and no meeting is recording, keeping the text in memory. Code is excluded because `includeCode` is off. Ask, Quick Recall and the Ask agent's `search_files` tool (cited as `[file:ID]`, the passage id) read it when the Files source is selected. External agents search it by words through `lokalbot-cli search-files` and the MCP `search_files` tool, only under the separate Files read grant (see [Agent CLI & MCP](#agent-cli--mcp)). Turning Files off deletes the index.
- **Agent notes** (Settings → Screen & Activity → Read coding agent notes, `LokalBot/Services/AgentMemory/`): off by default. `ClaudeCodeMemoryReader` reads `~/.claude/projects/*/memory/*.md` (front matter for the description and type, `MEMORY.md` only for titles, and the opening of one session file per project for the folder's real path); `CodexMemoryReader` reads `~/.codex/memories` (`MEMORY.md` split at `# Task Group`, `memory_summary.md` split at its sections, and `rollout_summaries/*.md`). `AgentMemoryExclusions` applies "Never read sessions in these folders" before a note leaves a reader, and every note's text passes `ScreenContextPrivacy.redact`. `AgentMemoryIngestor` scans off the main actor at launch, on a setting change and every ten minutes, and `AgentMemoryStore` makes `agent-notes.sqlite` in the library (a `notes` table plus an FTS5 `notes_fts`) match the scan; turning the setting off deletes the file. `AgentNotesIndex` (`CLISupport/AgentNotesAccess.swift`, shared with the CLI) is the query-only read side: words by BM25 with title and summary weighted, every word first and any word as a fallback, a prefix match on the last word, and a substring path for CJK. The notes are a search source only (`AskSourceScope.agentNotes`, `AskFacet.agentNotes`, the Ask tool `search_agent_notes`, `[note:ID]` citations, a Quick Recall section); they never feed the day digest, Dream, or Personal Context. There are no vectors yet, so search is by words. `AgentMemoryReaderTests` and `AgentNotesTests` cover it. The Windows and Linux app has the same source: the readers and the ingestor thread are in `LinuxWindows/crates/lokalbot-engine/src/agent_notes/`, the store, the read-only index and the grant in `crates/lokalbot-core/src/agent_notes/` (the same file and schema, so either app reads what the other wrote), and `search-notes` / `search_agent_notes` in `crates/lokalbot-cli/src/notes.rs`. There the setting is under Settings → Day Memory and the grant is its own switch, **Allow external agents to search agent notes**, in Settings → Privacy & Data.
- **UI:** sidebar Today | Actions | Meetings | Timeline | People | Projects | Ask | Agent, with Settings in its foot (it opens the Settings window). Ask is one field (`AskView`, routing in `AskRouter`/`AskPhase`): typing lists matches (`AskMatchesList`), under the field on a new question and in a tray above the docked field inside a conversation, so the conversation stays on screen. **Return asks**, whatever was typed; **Down Arrow** moves onto the matches (`AskMatchCursor`) and Return then opens the selected one with playback paused, without starting inference; Escape returns to the field and then folds the tray. The button always says Ask, is disabled while the field is empty, and becomes Stop while an answer is written. Quick Recall keeps Return for opening a result (see **Quick Recall** below). What the answer reads depends on what was typed (`AskAnswerScope`, using `AskIntent`). A full question (two or more words ending in a question mark, three or more words starting with an English question or request word such as what, who, how, did, summarize, list, or any four or more words, so a question in another language without a question mark counts: `AskAnswerScope.isFullQuestion`) reads everything in the sources and dates chosen in the composer's two menus, whether or not matches are listed; the listed matches never narrow it, and the sources menu keeps showing the chosen sources. A keyword or short phrase is a search the person then asks about: its answer is bounded to the listed meetings and screen moments, including folded lines and attached screens (`RecallWorkspaceState.selectResultEvidence`); a selected Activity source stays available, since activity has no result rows to bound, and so do Files and Agent notes when files or notes matched, and the sources menu then names that limit. With no matches, or for a "Remember …" statement, nothing is bounded. Scope set on purpose applies to both kinds and shows in the sources menu until it is widened there: a meeting or screen moments another page handed over ("Ask about this meeting"), an attached screen, and the menu's "Only …" state left by an earlier keyword. Because a full question is no longer narrowed by its matches, it is an unscoped question whenever the menus say All sources and Any time, so it gets work memory and learned Personal Context items like any other unscoped question (`ChatViewModel.run`). Scope lives only in the composer's two menus. The sources menu (`AskScopeSummary`) toggles Meetings, Activity, Screen, Files and, while Read coding agent notes is on, Agent notes, holds the match-type and screen-app filters as submenus (they constrain the listed matches only), and links to source permissions; its button names the active filters and, when a question is limited to earlier matches or to evidence another page handed over, what it is limited to, with a row that widens it again. The time menu offers Any time, Today, Yesterday, Last 7 days, and a specific date across meeting, activity, and screen search and answers. Empty results offer Clear search filters. Civil-date ranges persist with questions and survive reopening, retries and Ask again without widening retrieval. Keyword and available semantic rankings blend automatically, respecting the semantic-indexing preference. Reading excerpts remove generated metadata and malformed repetition; semantic meeting hits recover the original indexed passage instead of displaying an old truncated embedding prefix. Keyword matches appear first and semantic ones carry a **Related by meaning** mark. An empty page suggests questions built from the latest own meeting, a person and a project already loaded (`AskSuggestions`), plus one word to search; with none of those it shows the general suggestions. In an answer a citation number is a pill that opens the quoted passage in a popover (`CitationPassagePopover`: the transcript line at the citation's second, a screen moment's stored text, a file's excerpt, or a saved agent note's summary, with Play from there or Show in Finder and a link to open the source), and one sources list ends the answer (`AnswerSourcesList`, grouped by `AnswerSources`; numbers are never renumbered) with a row for what the person told LokalBot when that was used. A failed answer shows a short notice with Model settings and Retry and lists the question's matches again, searched on the Mac within the scope recorded with the question. A line under the field appears only for a remote model or a blocked model connection.
- **Quick Recall** (`QuickRecallView`, the `quick-recall` window): one small window for search, commands and Ask. The system-wide shortcut (Settings → Ask → Quick Recall, off by default), ⌘K and View → Quick Recall… all open it through `AppState.openQuickRecall`; the separate ⌘K command palette window is gone and `PaletteCommandCatalog` feeds this window. Before anything is typed it lists Recent (recent meetings and saved screen moments merged by time, `QuickRecallRecent`) and every command with its shortcut (`PaletteCommandFilter.idleOrder`: recording and dictation first). Commands that act on the main window's current page (the Agent screen's, and its tasks) are offered only when the window was opened from the main window (`quickRecallOpenedFromMainWindow`). Typing searches with `RecallSearch.search`, as before, and groups the rows in a fixed order (`QuickRecallGrouping`): commands whose words start with the typed words (`PaletteCommandFilter.split`), Meetings, Screens, Files, Agent notes while Read coding agent notes is on, and last the commands that only hold the typed words somewhere (so everything the palette found is still found, but Return on a search word never runs a command that merely contains it). Each kind lists three rows; its heading's **Show all N** opens Ask on the search with the sources narrowed to that kind (`AskNavigationHandoff.sources`), and for commands lists them all in place. The search lists at most `RecallSearch.displayLimit` of a kind, so a kind that filled it while the result says more matched reads "40+", never an exact total. A row (`QuickRecallRowModel`, `QuickRecallRow`) is two lines: a tile (a screen moment's thumbnail with a badge when it is saved, a waveform, the file's own icon, a command's symbol), the title, the app or folder in grey and when (`QuickRecallDateLabel`), then the matching line starting with who said it (`SearchIndex.Hit.speaker`), or with Your notes, Summary or Outcome, or a PDF's page. **Return opens the selected row; ⌘Return asks**, and so does Return once the arrow keys are on the Ask row pinned under the results (`QuickRecallCursor`; with nothing to open, Return does nothing). The field is an AppKit text field (`QuickRecallTextField`) that owns both typing and the list's keys, as the palette's field did, so a typed character cannot arrive twice; it takes focus without activating the app or ordering a window. Asking answers in the window: a new conversation in the shared `ChatViewModel`, shown by `ChatTranscriptView(style: .compact)` with sources as numbered rows (`QuickRecallAnswerSources`, quotes marked by `QuickRecallQuote`), a back arrow to the results, the field as "Ask a follow-up", and a foot that says where it was answered and what it read, with Copy and **Continue in main window** (`continueQuickRecallConversationInAsk`, which also sets the Ask screen's sources menu to the question's scope). What the answer reads is `QuickRecallAskScope`: a word or a phrase of up to three words is limited to the listed meetings and screen moments (all the search listed, not only the three shown), exactly as ⌘Return's handoff was; a full question (`AskAnswerScope.isFullQuestion`), a "Remember …" statement, or a search that listed no meeting or screen moment reads every source. A word asked while its matches are still being found waits for them. The Ask row names a remote model before anything is sent; remote-inference consent and the About-you gate are `ChatViewModel`'s, unchanged. `QuickRecallResultsTests`, `QuickRecallRowModelTests`, `PaletteCommandFilterTests` and `FocusOnAppearTests` cover it.
- **On screen during a meeting:** captures stamped with the meeting id (plus unstamped legacy captures inside the call) become `MeetingScreenContext`: the Summary tab lists documents, pages, and windows that appeared (excluding the call itself), each able to play from its first appearance or open the retained capture, and the Transcript tab shows the window on screen at the playhead. Titles, document names, and URLs only; retention applies.
- **Player:** mic + system tracks play in sync (shared device-time anchor). One slim bar under the meeting's header stays in view on every tab: play/pause, who is speaking and the line at the playhead, **Show in transcript**, the waveform, time and speed. A ▶ time on a decision, action or transcript line plays from there in place; the currently-playing transcript line is highlighted.
- **Meeting page:** a compact header carries the one title, a date line (date, length, app) and who spoke; the tabs are Summary, Transcript and Notes. Summary leads with the outcome: a bulleted recap (whole points expand after five), decisions, actions split into **For you** and **For others**, open questions, and the full notes behind **Full summary**. Find-in-page opens the full notes automatically when needed. Processing badges remain on library rows; failures expose a conditional retry banner. The toolbar keeps **Ask about this meeting**, a **Share** menu with every copy and export, and a short **…** menu.
- **Speakers, owners and refresh:** unnamed call voices show in the header with **Name N speakers…**, which opens one sheet: bounded excerpts (at most 12 seconds), a sample quote, speech time, invited names, or a typed one; a voice recognized from earlier meetings is offered already picked and is saved only with the sheet. Each action owned by someone else carries its owner as a menu (you, this meeting's speakers, invited people, no owner), amber while the owner is missing or still an unnamed voice. When a speaker change archives the old extraction, the Summary keeps showing those decisions and actions, owners stay correctable, and a banner offers **Refresh summary** with the selected inference destination; archived actions stay out of the current action index until refresh. Saved action corrections remain separate from regenerated extraction. Mixed or unresolved voices are never silently named.

## Ask assistant — conversational Q&A over your library

- **Chat with your meetings:** pressing Return in the **Ask** section sends your question to a conversational assistant over your library — ask what was decided, find action items, or search transcripts in natural language. A small ReAct agent (`ChatAgent`) reuses the selected `TextEngine` and calls tools to ground every answer. With the built-in default it stays on the Mac; an approved remote backend receives the prompt context needed to answer.
- **Tools (pi-agent style, mirroring the CLI):** `search_meetings` (FTS5 keyword + optional semantic search), `list_meetings` (filter by title), and `get_meeting` (read a meeting's summary, or its transcript one 6,000-character window at a time; a cut window names the timestamp to continue from with `from=HH:MM:SS`). The agent picks a tool, reads the observation, then answers — citing meeting titles and dates, and saying so plainly when nothing matches.
- **Limits:** the system prompt ends with the current local time so relative dates resolve. Each turn replays up to 16 recent messages within 12,000 characters, never starting with an answer whose question was cut, and allows six tool calls before a forced answer that must say what it could not check. Apple Intelligence keeps four tool calls and eight messages within 4,000 characters for its small window.
- **Robust protocol:** tools are advertised in the system prompt with the recent-meeting list as ambient context; a tool call is parsed from a JSON object **or** a model's native `name(arg=…)` function-call form (smaller Qwen models emit the latter), with a tolerant fallback to a plain answer so a sloppy reply never hard-fails.
- **Reuses the configured backend:** built-in llama-server by default, or Ollama / OpenAI-compatible / Apple Intelligence / ChatGPT plan / Claude plan — the same Settings → Models choice.
- **Personal Context (personal world model, phase 1):** a message starting with "Remember …" (`RememberIntent`) is saved as a `PersonalClaim` by `PersonalModelController` without a model call; the reply is a receipt turn that stays out of model history. Each question gets a `PersonalContextBuilder` selection (Always use, principles and preferences, then facts and goals sharing words with the question or the previous two user turns, within 2,000 characters) placed after the library overview and before work memory, and the answer records `usedClaimIDs`. Stated claims carry no evidence, so scoped questions get them too. Settings → Personal Context (its own tab, `SettingsTab.personalContext`, `PersonalContextSettings`) edits them; `AppSettings.askMemoryEnabled` gates saving and use. Headless `--chat` builds the same block. After each overnight review, `AppState.learnAboutPerson` (when `personalLearningEnabled` is on) first runs `WorkMemoryPromotion`: Dream goals or projects kept 14+ days become review suggestions. It then runs `PersonalLearning` on that day's own-microphone lines (`ownTurns`: microphone segments attributed to the user, no echo or overlap; plain `local` and `local 1` are one voice; with several numbered voices only one that has 4× the next counts, else the meeting is skipped; a confirmed voice wins) plus typed lines from `PersonalLearning.typedLines`: coding-agent requests and Ask questions, which always go to review. With `personalLearningFromDictation` (off by default; `AppSettings.learnsFromDictation` also needs Ask memory and learning), `DictationCoordinator` hands the raw spoken words of each paste into an identified field to `AppState.keepDictationForLearning` after `CotypingAXHelper.dictationLearningSurface` reads the window title and page address once and `DictationLearningPolicy` applies the nearby-text exclusions (apps, websites, private windows, LokalBot itself, unreadable browser pages). `DictationLearningLog` keeps them sealed with the chat key in `memory/dictation-for-learning.json.enc` (redacted, at most 200, two days); the learning pass reads its day as `.typed(.dictation(app:))` lines, skips ones already read as an agent request, and then deletes the day. Items in the line's language are grounded by word overlap; an item the model translated is compared with `EmbeddingIndex.similarityVectors` (local, never downloads), and uncertain ones become suggestions. Grounded facts and goals are saved as learned, preferences become suggestions, and learned items retract through `DreamStore.evidenceCheck` when their meeting changes. Items marked Share with agents reach external agents only through the separate Personal context grant: `PersonalContextAccessManager` mirrors them into `control/personal-context.json` on every change, and `get_personal_context` / `lokalbot-cli personal-context` rank them with the same `PersonalContextSelection`. See `Docs/personal-world-model-rfc-2026-10-14.md`. Each pass records the day and a SHA-256 `fingerprint` of its non-dictated lines in the personal model's `learnedDays` (60 days); a rebuilt review with the same lines doesn't call the model again. When a learned claim's evidence revision is invalidated, `retractInvalidated` asks `learnedClaimSourceStillQuotes` (that meeting's `ownTurns`, that day's agent requests, or work memory) and re-stamps the claim to the current revision if its quote is still there; otherwise it is retracted.

Individual and overlapping blocks stay intact; brief app interruptions do not force a new session. These labels describe captured evidence, not inferred tasks.
- **Today:** the default landing page combines capture state, the current day digest, open meeting actions, upcoming-meeting preparation, and direct routes to Ask, Timeline, and Agent Mode. The reading column puts decisions and next steps before the current work summary. The shared digest keeps freshness in a compact footer and the expandable Yesterday recap below current work; previous-day provenance is inside that disclosure. Calendar setup lives in Settings. - **Timeline:** one day as its page beside a rail. The date is the window's title (`TimelineContentView` in `CaptureView.swift`): it opens a calendar, with previous/next arrows, a Today button on other days, and **Ask about this day** beside it. A row has two lines: the title, then project and what was produced for work ("Atlas · 1 PR opened", from `TimelineWorkSession.projectLabel`/`taskTitle` and its agent outcomes) or "Meeting · app" for a meeting, with the duration at the right. A session spent in the app a recorded meeting ran in folds into that meeting when the meeting covers at least 60% of it, so a call is listed once; work with a project or coding-agent sessions is never folded, and the folded activity stays under All captured activity. The main area shows the day's page (`TimelineDigestPage`) until a row is chosen, as panels (`SectionPanel`) that fill it inside 24 pt gutters, up to 1,100 pt: **Highlights**, whose footer says when the digest was written, with **Update** when there is newer activity; **Actions from this day's meetings**, the shared `ActionThreadRow` rows with an "N open" badge and a link to Actions, or the header alone with "All done" (`TimelineDayActions`); **Work Summary**, with Blocked and In progress, project tags in the sessions' colours and their next step, and Done folded into one line, or an older digest's plain entries; and **Decisions** when the day has them. A day without a digest shows an invitation with **Write Digest** in the Highlights panel; a stale digest stays visible, marked. Choosing a row, or a bar of the strip, shows it in the main area while the rail stays: a session's title panel (project, time range, active time and apps), then panels for what the coding agent was asked and recorded doing, its screen moments as thumbnails with **Show all**, and what was open (each title opens the activity behind it); a meeting's short preview (recap, your actions, decisions, **Open meeting**). **All captured activity** keeps the per-block hour track for exact evidence and **Delete screen moments…**, the reviewed time-range deletion of screen captures. **Day digest** above such a page returns to the day, as does choosing the selected row again; an activity block or a screen moment opened from a page has a link back to it. Up and Down in the rail walk the sessions: Down from the day's page chooses the first one, Up from the first returns to the day's page, and Down from the last chooses All captured activity (`TimelineListSelection`). The body keeps the page (420 pt minimum) beside the rail (260 pt at its narrowest), so below that the window stops shrinking instead of switching to a drawer.
- **People:** `PeopleDirectory` joins calendar attendee names, speaker names the user applied (and their calendar-identity links), and action owners into one person per attendee address (used only as a private join key, never shown or exported), or per full name. An attendee without a display name takes the rename picker's address-derived name, except single-word mailboxes on public providers, which are usually handles. A lone first name joins the one person whose full name starts with it. Speaker labels, group or role owners ("Engineering team", "Product/research"), owner lists ("Matt, John, and Emil"), merge suffixes, and the Mac account's name are never people. Corrections the user makes on the page (`PeopleStore`, `people/curation.json`, keyed by opaque person ids) apply on every build: a chosen name is shown and also recognized as a name, merges run after the automatic joins and again once action owners are known (the target keeps its name, and **Separate** undoes one), and **Not a person** removes the entry from People, Projects, and the CLI. Recordings of one calendar event on one day, or without an event the same title starting within 15 minutes of the previous recording's end, count as one meeting that opens its longest recording; meetings are grouped by title. Each person lists what is waiting on the user (open actions naming them or from meetings with at most two other people) and on them, with **Still open?** on open work no meeting has mentioned for 21 days and that is not due ahead; **Last time** (or **Last mentioned**), up to three summary lines from the newest of their last eight meetings that the person said (an applied speaker name) or that name them with a capital letter (a name that is also a common word does not count at a sentence start), skipping action and decision sections, or a meeting's overview lines when it was only with them; projects whose names appear in those lines, their open work, and decisions with them; decisions from meetings of at most four people, or in larger meetings only those they said or that name them; and meetings together by title. Decisions of one meeting keep one order between rebuilds. The page (`PeopleWorkspaceView`, `PersonDetailView`) shows only sections that have something in them: the next calendar meeting with the person as a card with **Prepare** (the same Agent prompt as the menu's **Prepare in Agent…**, built by `PersonPreparation` from the person's notes, projects, open work and decisions, with nothing from the calendar event), **Open between you** as one section with an amber "You owe <name>" label and a grey "<name> owes you" label over the shared `ActionThreadRow`, **Last time**, and **Decided together** (three, then **Show N more**). Projects, Meetings (titles with their count and last date; a series opens to list its dates) and Names sit in a side column that moves under the page when the pane is narrower than `PageSideColumnLayout` allows; the toolbar holds the person's name, how long you have been meeting, **Ask about <name>** and the … menu (Prepare, Draft follow-up, Rename, Merge into, Separate, Not a person). The list (`PeopleListContent`) is grouped by time only: **Coming up** (people in calendar meetings in the next seven days, by meeting time), **Last 2 weeks**, **Earlier**, each by when you last met; a row shows the next or latest meeting and one badge, "You owe N" (amber) or "Owes you N", the user's own first when both are open. `PeopleUpcomingMeetings` matches the coming week's events (`UpcomingMeetingSchedule.readAhead`, read only while Calendar use is on and access is granted, never requested from People, refreshed each minute while the page is open) to people by the keys the directory registers: an attendee's address, else the full name of someone known only by name, and for an attendee without an address the one person carrying that full name or whose full name starts with a lone first name; two people who share a name are never guessed between, an event some recording already covers is left out, and the match is kept in memory only. People never reads voice profiles. `WorkspacePageBlocks.swift` holds the list-and-page pieces People and Projects share (`ListColumnSearchField`, `PageSectionHeading`, `PageDecisionRow`, `PageWithSideColumn`, `SideColumnBlock`, `LabelChip`). Actions can be filtered by person. `WorkMemoryConnections` rebuilds People and Projects off the main actor, reading transcripts for applied names only from the last 180 days, and whole summaries and `transcript.md` for Projects and person notes from the last 120 days, each cached by file date.
- **Projects:** the person tracks projects (`ProjectStore`, `projects/tracked.json`: a name, other names, and hidden suggestions); everything else is derived. `ProjectLinks` joins each tracked project to meetings from the last 120 days whose title, whole summary, outcomes, or transcript contain every significant word of one of its names; actions that name it or come from a meeting whose title names it; decisions naming it; overnight review projects whose names it covers; people from its meetings; and the last seven days of window time whose titles name it, per day, with the six longest windows and a count of all of them. Actions are split into the user's, other people's mentioned in the last 14 days or due ahead, and older ones. Each meeting carries the first summary line naming the project, else a transcript line with its time, else the action or decision, cut to 180 characters around the name. Suggestions are names `ProjectTopicDetector` finds and overnight review projects no tracked project covers. The detector keeps proper nouns that are nearly always capitalized and appear in at least three meetings' titles, summaries, actions, and decisions, excluding people's names and short forms, app names, and generic work vocabulary; a capitalized sentence start ("**Them 4:** Vireo…") counts only for a term also seen capitalized mid-sentence. **Where it stands** (`ProjectStatusGenerator`) asks the Think model for an overview, up to five points citing their meeting, and open questions from the ten newest meetings' lines, decisions and open actions, and review notes; notes are saved in `projects/summaries.json` with a hash of that evidence, kept and marked "Newer evidence since this was written." when it changes, and written automatically on open only under `allowsAutomaticMainInference` with a ready model, once per evidence version. Deleting a meeting (`withPrimaryEvidenceChange(.removal)`) withdraws every note that used it. The list (`ProjectsListContent`) has a search field and the add button as its header, then **Tracked**, most recently active first, each with "Active today", "Active yesterday", "Last active <day>", "Quiet since <date>" once nothing has named it for `quietAfterDays` (the same 14 days as `ProjectLinks.recentOthersActionDays`; such rows are drawn fainter) or "Nothing linked yet", and the count of the user's open actions; then **Suggested**, with a dashed monogram and "In N meetings" or "From overnight review". Hidden suggestions come back from the link at its foot. A tracked project's page (`ProjectDetailView`) leads with the **Where it stands** card, the only model-written block: a sparkle, one line from the saved note saying when it was written, by which model, and on this Mac or which server (`ProjectsWording.provenance`), and **Update** (or **Write note**); while a new note is written the old one stays, dimmed. Facts follow outside the card: **Your actions** and **Waiting on others** (three, then **Show N more**, recent before older) on the shared `ActionThreadRow`, **Decisions** with their meeting, and **Meetings** (four, then **Show all N**), each with the line that names the project and a ▶ time that plays a transcript line. Overnight review notes are evidence for the note and are not listed on a tracked project's page. A side column (`PageWithSideColumn`, as in People) holds **Last 7 days** (the total, a bar per day from `ProjectTimePresentation.days` with zero for a day without time, the three longest windows and "N more windows"), **People**, and **Names** with **Edit names…**. A suggestion's page opens on the decision in one card: where it came up (the overnight review's own words carry the sparkle), then **Add to <project>** first when that tracked project already has at least half of the suggestion's meetings (`ProjectSuggestionHome`), with **Track as its own project** and **Not a project**; otherwise **Track** first, with **Add to a project** and **Not a project**. Tracking opens the new project, adding opens the project it joined, and **Not a project** opens the next suggestion. A tracked project nothing names yet is one centred message with **Add other names…**, which opens the names sheet. The toolbar holds the project's name, its last activity (or "Tracked since <date>", or "Suggested"), **Ask about <project>** and, for a tracked project, the … menu (Edit names…, Merge into, Stop tracking).
- **Morning brief actions:** Dream action candidates carry `[A1]`-style handles; the model is asked to begin a top action with its handle, and `DreamPrompts.linkTopActions` maps handles to thread ids (`DreamReport.topActionThreadIDs`), so linked actions render as checkable threads. The evidence-only fallback links its ranked threads too.
- **Day digest:** "Write digest" / "Update digest" runs the configured LLM over the day's blocks, meetings, and captured text → `journal/YYYY-MM-DD.md`. The same digest is visible from Today and Timeline, can be copied or exported, and grounds **Ask about day**. Each evidence segment is extracted separately: substantive work leads the task list, and lighter but identifiable work follows it instead of being dropped. A segment, about an hour of continuous activity, returns its main work item plus up to two other distinct items (`other_tasks`), so an hour that interleaves a fix, a review, and an email need not pack them into one line. On the synthetic benchmark in `Benchmarks/DayDigest/` this raised items with their own task line from 34% to 62% with Qwen3.5 4B. Work done through an AI assistant or coding agent counts as substantive when the evidence names a concrete task. External Think servers share one request gate per origin (`RemoteInferenceGate`): processing runs at most two requests at once, scheduled work (digest, Dream, briefs) on at most one of them, meeting notes at `pipeline` priority ahead of it, chat, dictation, and agents never queue behind processing, and a 429 pauses the whole origin for `Retry-After` or an exponential cooldown (2–60 s). The gated engine retries transient errors (429, 5xx, dropped connection) up to five attempts for notes, four for scheduled work, and two for chat, so callers do not replay on top. Segments are sized by active time: one per hour of a session (never more than it has events), at most 16 a day, instead of a fixed eight. Answers to unchanged segment and aggregation prompts are reused from an in-memory `DayDigestSegmentCache`, purged for a day whenever its evidence is deleted or corrected. After an evidence change the scheduler waits 20 s for notes, outcomes, and indexing to settle, and keeps a failure's 15-minute backoff.
- **Coding agent sessions:** on by default, chosen in setup's first step and in Settings → Screen & Activity. A new install reads nothing until setup is finished: the ingestor's configuration has no agents until `AppState.onboardingShownKey` is set, and `AppState.finishOnboarding` starts it. While enabled, `CodingAgentEvidenceIngestor` reads Claude Code and Codex transcripts (`LokalBot/Services/CodingAgents/`) for the digest's seven-day window every ten minutes and before each digest run. It splits sessions into bursts at ten-minute idle gaps and stores only settled bursts in `coding_agent_bursts`, so a digest's inputs cannot change while it is written. Removing or correcting a stored burst, for example after a folder exclusion or a deleted session, goes through `withPrimaryEvidenceChange` as a revision; only **Delete saved agent sessions** withdraws the generated journal. An unreadable transcript never counts as a deletion. Bursts follow screen-text retention. The journal lists them under `## Agent sessions`, using recorded facts only: requests, actions, PRs, and changed files. The model reads each burst as `WORK SOURCE: AGENT SESSION` evidence. A segment merges a session's bursts into one detail and reserves up to six of its twelve detail slots for sessions, those with recorded outcomes first. While a session covers the time, screen text from agent host apps (Claude, Codex, terminals, editors) keeps one sample. Segment extraction yields one task per segment, which would drop parallel sessions. So each session that recorded an outcome (except scheduled runs) also becomes a task stated from its actions. These tasks are added after aggregation, merging into a model task only when the titles match. Scheduled runs' reports are withheld from the model because they often describe other days. Bursts also fill the fallback task list. Days without bursts keep their previous evidence signatures.
- **Scheduled digest and Dream:** automatic digests preview today after the configured hour and finalize every missed day of the last seven, oldest first, once its journal predates that day's end; days without evidence are skipped. Overnight review catches up the same seven-day window after its hour once LokalBot is not recording or processing and the Mac is on AC power. Both use the Think connection's origin approval (or the selected plan's approval); there is no separate scheduled-run approval.
- **Background work card:** `BackgroundActivityMonitor` combines published state from the processing pipeline, day digest runs (segment progress), the Dream scheduler, model downloads, and the semantic backfill into the sticky sidebar card above the storage summary. It shows the highest-priority activity, lists the rest in a popover, and routes each row to its meeting, day, Today, or Models settings.
- **Digest provenance:** version-2 metadata fingerprints the exact digest inputs and generated journal bytes. Dream, exports, and routines reuse a digest only while both match, including after corrections or deletion of the last source. Legacy unsigned journals remain readable but are not reused as verified evidence until regenerated. Automatic repair preserves edited signed journals; explicit meeting/screen deletions invalidate dependent day products. Only those deletions (`AppState.EvidenceChange.removal`) withdraw a generated journal. Reprocessing, transcript and outcome edits, saved moments, and re-read agent sessions are revisions: the journal stays, shown as out of date, until the scheduler or the person regenerates it. Before 2026-10-07 every revision deleted it, so a summary rerun right after a manual digest made the digest vanish. Days older than the retention window are never shown as out of date for a fingerprint mismatch alone, because expiry, not new work, explains it.
- **Refresh ordering:** generation rechecks the journal revision before saving, preserving edits made while the model runs. Persisting a digest reopens exports and routines that may have finished earlier. Meeting edits invalidate every Dream report whose 14-day comparison window includes the source. Screen, activity, coding-agent, and past-day digest changes are activity-only: they revoke the reports and memory that read that day's screens or digest and leave meeting-derived facts alone; today's digest refreshes revoke nothing. Scheduled retention is not such a change: expiring screen text, titles, and agent sessions (`AppState.withScheduledRetention`) leave that day's generated journal, Dream reports, and work memory, which outlive the screen window. The journal is not reconsidered either, so it is never rebuilt from what retention left. Settings → Overnight review → **Clear work memory** deletes all of them; a dream that started before the clear cannot write back (`DreamStore.clearAll`). An in-flight generation is checked against its own sources when it commits, so an unrelated change no longer discards it. Dream's 24,000-character evidence gives the day's journal at most 12,000: its summary, meetings, agent sessions, and time allocation first, then as much of the raw activity log as fits, so app totals, saved moments, the comparison window, and action handles always arrive. Dream requests cap output at 4,096 tokens and reasoning at 1,024; an automatic run that hits a rate limit or dropped connection is retried after the 15-minute backoff, and only the third consecutive failure for a day writes the evidence-only brief. The retention pass records its last run in the library (`.screen-retention-last-pass`), so relaunching does not repeat it.
- **Dream retraction:** app-owned provenance follows facts across memory merges. Source deletion/correction retracts dependent projects, goals, patterns, and reports, including pins; unattributed legacy facts are conservatively removed on evidence mutation. Stable meeting IDs and conservative civil-date coverage handle timezone changes. A root-level revocation intent and process-shared lock protect source writes and prevent stale in-flight commits or restart recovery from reviving withdrawn facts. Automatic screen retention uses the same boundary and deletes only reviewed rows.

## Autocomplete (Cotyping engine)

- **Ghost text everywhere:** as you type in almost any macOS text field, a gray suggestion appears next to the cursor; press **Tab** to accept the next word or phrase (Settings → Autocomplete → **Each accept takes**), **`** to accept the rest, keep typing, or press **Esc** to dismiss. The subsystem remains named Cotyping in source and settings keys. Its Accessibility poll resolves the focused field and caret, a `CGEventTap` watches keystrokes, a borderless click-through `NSPanel` renders at the caret, and accepted text is inserted as synthetic Unicode keystrokes.
- **Flow while accepting:** a suggestion starts at up to four words (Settings → Autocomplete → **Suggestion length**). While it is accepted or typed through, `CotypingSuggestionExtension` tops it up once two words are left, so the ghost stays a few words ahead until the sentence ends; words already shown never change, and a sentence that ended is not continued. Tab takes a word without its trailing punctuation unless **Accept punctuation with the word** is on. Escape on a visible suggestion dismisses it without reaching the app and holds that field for ten seconds (**Escape on a suggestion** can send the key through; a composing input method always receives it). Search fields stay quiet. These follow a live comparison with Cotypist recorded in [Docs/CotypingParityQA.md](Docs/CotypingParityQA.md).
- **Fields that report no caret:** some fields, such as Chrome's text areas and Qt Quick apps like Viber (whose text accessibility answers every character with an empty rect), answer every caret query with an empty box. With Screen Recording already granted, `CotypingVisualCaret` captures the field's frame (at the display's own scale, or three times its points on a non-Retina display), finds the line that ends at the caret with Vision's fast text recognition, and keeps only the caret's position: the line's end is aligned with the typed text, the font is sized from the typed text rather than the recognized one, and a caret bar read as "|" is taken as the caret. A caret line in Cyrillic, which fast recognition cannot read, uses accurate recognition (Russian and Ukrainian models, with the letters they lack such as ђ and љ excused) to decide which line it is, and `CotypingVisualCaretInk` measures that line's edges, baseline and caret bar from the capture's pixels, since accurate recognition gives only loose word boxes; a line over a picture rather than a flat background stays a popup. Typing along that line moves it by text width, measured again in the background every dozen characters (every four on a Cyrillic line) and found anew close to where the line wraps. Until the caret is found, nothing is shown rather than a popup beside the field; after three finds in a row fail in a field, that field gets the popup. Without Screen Recording, or in excluded apps and sites, the suggestion is shown as a popup just outside the field, never over its text.
- **Never over text:** a key that leaves the suggestion takes the ghost down at once, without waiting for the app to publish the key. Typed and accepted text moves the ghost by its width as the app draws it, spaces included, and once the app publishes the caret the ghost moves to it whenever it would cover typed text. Wrapped lines go only onto empty lines inside the field; a suggestion that does not fit is cut after the last word that does, and the session keeps only what is shown, so the accept keys never insert unseen words.
- **Its own dedicated on-device model:** Autocomplete decodes a dedicated model (recommended **Gemma 4 E2B Base**) **in-process via libllama** for low latency, with the localhost `llama-server` as the fallback. The prompt treats the model as a pure text continuer; a shared normalizer strips chat/`<think>` scaffolding, prompt echoes, and trailing-text duplication, then collapses the result to one line.
- **Or a server:** the Autocomplete picker in Settings → Models (On this Mac / Think's server / Another server, edited as a `CotypingServerDraft` and applied with Use model) can send completions to Think's server (with Think's model or another one there) or to any OpenAI-compatible server, hosted or on another device, including over Tailscale. `CotypingEngineSelector` then routes to `RemoteCotypingEngine` (`CotypingServerRoute.swift`), frees the on-device model and uses the model-server debounce. The automatic request type tries raw `/v1/completions` on self-hosted and generic servers and chat (`ChatContinuationEngine`, thinking off) on OpenAI, Anthropic and OpenRouter, and moves a server to chat after a 404/405/501 or a "not supported" answer. A chat reply cut off at its limit keeps its text; one that ran out inside reasoning the model cannot turn off is asked again with room for it, and that model keeps the room until LokalBot quits. Chat models often leave out the space before a new word ("at a" + "higher level"), so after a whole word a reply that starts with a letter or digit gets it back (`CotypingEngine.restoringWordSpace`); without it the seam guard would drop the suggestion as a misspelling. Each request takes an interactive slot on the origin's `RemoteInferenceGate`, is never replayed, and is abandoned after 15 s. `RemoteCotypingEngine.problem` keeps the last failure or empty reply until a suggestion arrives, and Writing shows it, since typing in other apps shows no error. The rehearsal checks `contextEpoch`, not the live `generation`, so keys typed into it do not drop a slow server's answer, and it says why an answer became no suggestion. A non-loopback origin needs its own autocomplete approval (`approvedRemoteAutocompleteOrigins`); plain HTTP is accepted only for private-network hosts (`InferenceEndpointPolicy.isPrivateNetwork`). Choosing a server is consent: the Writing context and learning toggles apply as set, so whatever they enable goes to the server with the text before the caret.
- **Completion quality:** **Gemma 4 E2B Base (Autocomplete)** is the first-launch default and the Balanced local preset's autocomplete model (3.85 GB, intended for 16 GB+ Macs). Existing saved selections are preserved. **LFM2.5 1.2B Instruct** remains available in the Lightweight local preset. Prompts retain paragraphs, lists and caret whitespace, keep up to 500 words within the existing 2,500-character window, and use concise subject/topic context. Native decoding enforces a typed space and ranks compatible tokens for rare word fragments; actual token counts bound the context window. Base completion models are excluded from the Main LLM picker.
- **Visible reply context:** the **Use visible text above the field** setting (on for new installs; saved settings without the key decode as off, so earlier installs keep theirs) captures up to three visible Accessibility messages/labels (420 characters) in the focused input's column, within 600 points above it. A bounded 70 ms/180-node traversal selects geometry before text; no pixels, OCR or whole document values are read. Shared capture exclusions, autocomplete exclusions, browser-origin checks and private-window titles (`ScreenContextPrivacy.isPrivateWindow`) apply before reading content. The context is checked against the current settings and exclusions when it is read and again on Tab (`CotypingVisibleContext.Policy.permits`); Tab never traverses the screen. Unsupported or timed-out reads fall back to ordinary completion. Context-grounded text does not enter local learning. The native model [visible-context replay](Benchmarks/Cotyping/README.md#visible-context-and-memory-replay) uses the same traversal on synthetic AX trees.
- **Whole-window text:** the **Use the focused window as context** setting (on for every install, including saved settings without the key; needs Screen Recording already granted) reads the focused window through ScreenCaptureKit and Vision `.accurate` with automatic language detection (`.fast` drops every accent and all Cyrillic). `CotypingWindowTextCapture` runs one read at a time off the keystroke path: the first focus read in a field starts it, later reads reuse it and start a background refresh at most every 4 s; capture plus recognition measured 150–250 ms on a full window. The Accessibility walk for the privacy target (64 levels, no pane required) runs inside that read, so a keystroke only reads the field frame and window title for the key (`CotypingWindowText.key`: process, role, window title, field column). `CotypingWindowText.excerpts` drops lines inside the field, credential and instruction lines, then keeps 2,000 characters: the field's column above it nearest-first, then the rest of the window in reading order, placed before the conversation. A reread replaces the text in use only when it adds 12+ new characters, the title or URL changes, or the text is a minute old (`shouldReplace`), so the prompt start stays byte-identical and llama reuses its KV cache; a replacement triggers a background prefill. The prompt block (`Visible in this window:`) has its own budget ahead of the 900-character preface, and the autocomplete context is 4,096 tokens so a long draft plus a full window never truncates the prompt front. Window text replaces the Accessibility excerpts once present; it is held per field, forgotten with focus or policy changes, and excluded from learning like nearby text.
- **Relevant saved facts:** two independent, default-off settings allow meeting/work memory and screen-derived work memory. A local lookup selects at most two 180-character snippets, limited to the last 90 days, from current meeting notes, summaries, corrected outcomes, and attributed Dream projects/goals. The two grants are the whole permission to read saved work memory: they apply whether or not Overnight review is scheduled and never start a review; mixed provenance requires both source grants. FTS finds meeting candidates but never supplies prompt text. A fact qualifies only when its source is named (at least half of the title's distinctive words appear in the draft, window title, or selected visible text) or when it shares two distinctive words with the user's own draft or window title, one written as a name, or three when none is. Everyday wording, calendar words and app names (`CotypingMemoryContext.everydayTerms`) never count, a notes line that adds no word to its source's title (a heading) is dropped, and writing with no distinctive word returns before any file is opened. Visible text can name a source but never counts as the user's own wording. Settings shows each grant's effective state (available, unavailable and why, or nothing saved) and whether the last lookup found anything. Source edits/deletion or permission changes invalidate affected requests and cached suggestions; accepted memory-grounded suggestions are excluded from the learning store. Setup samples never retrieve private context. See the synthetic [memory replay](Benchmarks/Cotyping/README.md#saved-memory-replay), which scores ignoring irrelevant memory alongside recall.
- **Opt-in & private:** off by default; needs **Accessibility** + **Input Monitoring**. Never reads password/secure fields; honors a per-user app exclusion list (preseeded with password managers and terminals).
- **In-app preview:** Settings → Autocomplete → **Try it…** opens a rehearsal that runs the real prompt, model and normalizer before the feature is enabled system-wide; readiness is the page header's status lines. The rehearsal and the live accept tap share `CotypingContinuationAcceptance`, so a rehearsed Tab takes the configured word or phrase with the same spacing and punctuation, the full-accept key takes the rest, typing the suggested characters walks through the ghost, and moving the caret or typing anything else discards it. A synthetic sample conversation above the reply field stands in for nearby text when that grant is on (it goes through the same bounded selection; the screen is never read), and each optional source is listed as used, found nothing relevant, off, or unavailable. The menu bar provides the quick toggle.
- **Typing measurements:** generation latency alone leaves out the wait for the host to publish a keystroke, the pause before suggesting, context lookup, validation and the overlay. `CotypingLiveMeasure` records, per kind of app, the time from the last keystroke to a visible suggestion, whether an accepted suggestion then appeared in the field (`CotypingInsertionCheck` compares the published text with what was sent), and whether it was deleted or undone at once. Only the whole inserted text counts as arrived, and a check closes on its own after 1.5 s, so an app that ignores an insertion is counted and the compared text is not kept. Counts and timings only. Settings → Autocomplete → **Usage and timing** shows, copies and resets them; `--cotyping-measurements` prints them for scripts.
- **Statistics:** `CotypingUsageHistory` keeps per-day (92 days) and per-month counts, each split by kind of app and model, under `lokalbotv3.cotypingUsage`. A suggestion counts as shown each time a continuation is presented and as used at its first accept, so the share used never passes 100%; typing counts only where `CotypingAvailability` would suggest, and gaps of up to 1 s between typed characters give the typing speed that prices saved keystrokes (characters accepted minus accept presses; 40 words a minute until 200 gaps are measured). Typed characters update the store without publishing or writing; the next generation, completed suggestion or quit writes them. Settings → Autocomplete → **Statistics** (`AutocompleteStatisticsView`) charts words or share used by day or month and breaks them down by kind of app and, once there are two, by model.

## Dictation — system-wide voice typing

- **Hold ⌥ Space and talk** (or switch to toggle mode, or record another shortcut in Settings → Dictation: a key with ⌃, ⌥ or ⌘, a function key, or two or more modifiers alone such as ⌃⌥; the global shortcut pauses while you record. A modifier-only shortcut is observed, not consumed: push to talk starts after a 0.2 s hold, toggle fires on a clean release, and any other key pressed during the chord means it was another shortcut): a floating pill shows recording state and a live transcript while you speak; release, and the text is pasted into the focused app — or copied to the clipboard instead (Settings → Dictation).
- **Your ASR, prewarmed:** dictation reuses the transcription engine and language you picked under Models (Granite, Parakeet, Whisper, Qwen3-ASR, …) and prewarms it when the shortcut is armed, so short dictations start instantly.
- **When the transcription server fails:** a rejected key, an unreachable server or any other `RemoteTranscriptionError` does not lose the dictation. `DictationTranscriptionFallback` transcribes the same audio with a speech model already on this Mac: the first downloaded one of Qwen3-ASR 1.7B, Whisper, Qwen3-ASR 0.6B, Parakeet v3 or Ultra and Granite Speech, plus the English-only models when the language is set to English. It never downloads a model for this. The text is delivered as usual and the HUD says "Transcribed on this Mac" with the server's own message. With nothing on disk the dictation fails, and the HUD says why. Every dictation that ends without its text now shows its reason in the HUD (`DictationProblemNotice`, for ten seconds, even with the floating status off); before, the reason reached only LokalBot's own window, so a failed dictation into another app looked like nothing had happened. The live preview and meeting transcription do not fall back.
- **Considerate capture:** playing media (Spotify, Music, browsers, VLC, …) is paused before recording starts; browser pausing skips live streams and supported conference domains. Audio goes to a local 16 kHz PCM scratch file and is deleted right after transcription.
- **Headset-safe microphone:** dictation records through an `AVCaptureSession` (`CaptureSessionMicrophoneInput`) opened off the main thread, not the meeting recorder's `AVAudioEngine`. The engine stops on every hardware format change, and AirPods change format when their microphone opens, so the engine stopped, released the microphone, and restarted in a loop that kept only fragments. More than three microphone recoveries within 20 seconds end the dictation with what was captured and an error naming the cause. The HUD waveform moves only while audio arrives, and the compact HUD shows "Reconnecting microphone" or "Waiting for the microphone" in its place. Recovery events are written to `debug.log`.
- **Recording feedback:** the HUD bars follow measured microphone loudness (`AudioLevelMeter`), and the recording dot stays grey until the microphone delivers its first audio, when an optional sound plays. Esc cancels a dictation that is starting or recording. Trigger modes are Push to talk, Toggle, and Tap or hold (a tap under 0.3 s keeps recording until the next tap; a longer hold finishes on release). Settings → Dictation → Microphone chooses the input (`DictationMicrophone`); with AirPods, the MacBook microphone keeps the headset in high-quality audio. When another app has Secure Input on, the Dictation page and menu bar say the shortcut is hidden from LokalBot.
- **Paste delivery:** the text is pasted where dictation began. Text selected before dictating is replaced; a selection that changed, a different field, a password field, or a field Accessibility could not read copies the text to the clipboard with a message naming the reason. The dictated text is promised to the pasteboard and marked transient, so the old clipboard is restored only after the app reads it; if no app reads it within 1.5 seconds, the text stays on the clipboard. A password manager's concealed item is not put back. After the paste, the bounded text before the caret in the same field is read back for about a second (`DictationInsertionCheck`, comparing the last words); if a readable field lacks the text, the overlay offers to copy it. The shortcut never cancels a dictation that is being transcribed; while the speech model needs attention it retries instead. Optional Compose context requires an unchanged focused window and field and honors the shared app/domain/private-window policy and credential redaction. Compose requests never open a thinking turn (zero reasoning budget, temperature 0.2, at most 4,096 output tokens), so the rewrite is not delayed by reasoning.
- **Grounded Compose:** separate, default-off grants allow visible text above the field, meeting/work memory, and screen-derived work memory. Explicit writing requests such as “reply” or “draft” can combine the current conversation with up to two relevant saved facts; source titles must match the request or authorized screen context. Nearby text uses the shared 420-character Accessibility selection with a single background worker and a 150 ms deadline. Directly dictated sentences get cleanup without these sources, sent as a JSON transcript to a cleanup-only prompt that must not answer or carry them out and keeps numbers as digits (`DictationCleanupPrompt`); Transcribe stays verbatim and bypasses the model and context providers. A writing request starts with a command (“reply…”, “napiši…”, after optional filler such as “hey” or “okay so”) or is a relay aimed at someone else that points at context (“tell him the time from the message above”); see `DictationRequestRouting`. The older focused-window OCR option remains separate and may begin during recording; unused OCR is cancelled after ASR, and the prompt keeps the window's last 2,000 characters. Last result shows which context a Compose request used, and a Writing profile row links to the profile Compose uses for tone and terminology. Source/permission changes reject stale results. See the [synthetic dictation quality replay](Benchmarks/Dictation/README.md).
- **Opt-in & private:** off by default; needs the Microphone grant plus Input Monitoring for the global shortcut. Audio, transcription, and paste all happen on-device.

## Agent Mode — an embedded coding agent on your selected Main LLM

- **A coding agent in the sidebar:** the **Agent** section embeds the pi coding agent, preconnected to the same local Main LLM through an OpenAI-compatible shim — a coding agent running on your own GGUF (or whichever backend you configured). A persistent task list supports search, rename, pin, archive, and restore, groups tasks by day, and shows each task's status; refresh, the runtime check and clearing history are in its … menu and the Agent menu. Browsing saved tasks loads native Pi history without starting inference. Execution is limited to four live runtimes; idle saved tasks can release their runtime when another starts.
- **Conversation workspace:** a new task shows a heading, one line saying what the agent may do at the current access level, the composer mid-page and the starters; once it has a conversation the composer docks at the bottom. `AgentTranscriptLayout` (`Agent/AgentPresentation.swift`) regroups the transcript for reading without reordering it: while a turn runs, the agent's words show in full, each run of tool steps folds to one line that opens to a row per step, and the running step shows live; a finished turn folds its work into one "N steps" line above its answer, which carries a Changed files card (Open, Show in Finder) and Copy, Retry and More. Notices are never folded. `AgentStepWording` names each step from its tool and arguments ("Searched meeting library"); a `lokalbot-cli` call gets a name only when it is a single plain call, and any other command shows its text. The task's status (`AgentTaskStatus`) shows beside its title in the toolbar and on its list row. An approval is one card above the composer (`AgentApprovalPresentation`): a question naming the target (Create or Replace from a file-exists check), where the file is, a preview that opens in full, a count when several wait, the full path as a caution outside the working folder or inside LokalBot's own data, and where the result goes with a remote model. Deny sits apart from **Allow once** and, where `canPersistApproval` allows it, **Allow writes/edits for this task**. The results inspector lists changed files, steps and sources, and previews recorded output with copy and local export. Copy, edit as follow-up, review and retry, and branch from message preserve the original conversation and do not undo completed actions.
- **Composer and context:** drag in files or use the context menu and `@` picker to attach UTF-8 documents, text-layer PDFs, meetings, and separately authorized saved moments. Sources are reread on send, with limits of 10 attachments and 60,000 total characters. Explicitly selected meetings are attached as summary/transcript text; screen sources include retained text and notes, never pixels. The composer has three controls: attach, the working folder, and one access chip named for what the agent does on its own (**Asks first**, **Reads any file**, **Edits any file**, **Full access**). Its list holds the four `AgentApprovalMode` levels, which apply to every task, then the model with its destination and reasoning. A model that is not on this Mac also shows under the composer.
- **Follow-ups:** while working, the composer shows Stop and Send, and **Send** adds the message to an editable, cancelable host-side queue shown above the composer ("Sends when done"). **Send now** on a queued message takes it out of the queue and sends it as a Pi steering message, or as an ordinary message when the agent is idle (`sendQueuedNow`); a rejected one returns to its place. Stop and app relaunch pause the queue. Failed sends retain their draft and attachments for review.
- **Navigation:** ⌘N creates a task, ⌘⇧F searches tasks, ⌘⌥←/→ moves between tasks, ⌘F finds in the current conversation, ⌘L focuses the composer, and ⌘⌥B toggles results. Agent actions and tasks also appear in Quick Recall when ⌘K opens it from the Agent screen. Text zoom is available in the Agent menu.
- **Persistence:** `agent/sessions/tasks.json` stores task metadata, drafts, queued follow-ups, and attachment references alongside native Pi JSONL conversations. The latter contain the context actually sent. Archiving preserves both; **Clear saved Agent history** removes both after confirmation. A branch copies the chosen native conversation ancestry to an independent file; it neither replays tools nor rolls back files.
- **Pi's own network behavior is disabled:** pi runs with `--offline`, version checks and crash reporting disabled. Enabling Agent Mode downloads its runtime once — a checksum-verified Bun release from GitHub plus the pi package from npm, pinned by a lockfile bundled with LokalBot. Bun's transpiler cache, pi's compile cache, and jiti's extension cache are off (`PiLaunchPlanner`), so no compiled copy of pi or the approval extension is kept outside that runtime. LLM requests stay local with the built-in backend; an approved remote Ollama or OpenAI-compatible endpoint receives agent context when selected.
- **System prompt:** `LokalBot/Resources/pi/system-prompt.md` replaces pi's coding-agent prompt (`--system-prompt`), and the Windows and Linux copy in `lokalbot-agent/resources` must stay identical (a Rust test compares them). It tells the model what LokalBot remembers and which `lokalbot-cli` commands read it; the bundled `lokalbot-library` skill has the details. Keep that skill's frontmatter valid YAML, with no `: ` inside the description, because pi drops a skill it cannot parse without an error. Before each run the extension adds an `environment` section with the local date and time zone, whether the folder is the Agent Workspace or one the user chose (`LOKALBOT_AGENT_WORKSPACE_KIND`), and the model and where it is served. Pi folds a changed section into the leading system message, which small local models' chat templates require, so a resumed task never gets a second system message.
- **Workspace boundary:** new tasks use a sibling working directory outside the private library. Saved tasks rooted inside the library retain their history and drafts but cannot execute. Raw reads of protected library, runtime, and session paths enter the tool-approval flow when a broader parent directory is selected; the selected approval mode still applies.
- **You approve sensitive access:** the extension's gate is an allowlist. A read inside the selected workspace and outside the private library is the only tool call the extension lets through without raising a request. The host then answers one kind of raised request by itself at every level, the default included, when the model runs on this Mac: a read-only lookup of the user's own library, as `AgentApprovalPolicy.isLibraryLookup` defines it (one `lokalbot-cli brief`, `list`, `get` or `search` call of plain and quoted words, with only the options listed in `lookupOptions`, optionally followed by `2>&1` and `| head`/`| tail` with a line count, from the task's own working folder). A lookup's output is fed to the model, so `modelRunsOnThisMac` is true only while the controller's bound `modelContext` is `.onDevice`; with a server, a subscription plan, or no bound model it is false and the lookup asks, except for a handed-off task (`allowsLibraryLookups`) in the read levels, as before. Anything the policy cannot prove to be a lookup asks. Add an option to `lookupOptions` only when it neither writes nor reaches the network. The extension checks the file pi will open: it resolves the path as pi's file tools do (a leading `@`, `~`, file URLs, Unicode spaces, look-alike names, the session folder), and a path it cannot resolve asks. File and shell calls follow the selected approval mode. Any other tool (an MCP tool, codemode, or one a later Pi release adds) asks with its exact arguments in every mode except **Full access**, which approves every agent tool; it cannot be allowed for the session. Commands, and the arguments of tools without a dedicated preview, exceeding 65,536 JavaScript UTF-16 code units are rejected before approval; the host also rejects incomplete or truncated previews. Approved shell commands run with your macOS user permissions and may access files or the network.
- **Inference redirects:** native buffered/streaming HTTP requests follow redirects only within the original scheme/host/port. The Pi provider uses its own scoped fetch adapter that rejects all redirects and validates the initial origin. Configure a server's final endpoint directly; inference approval does not authorize forwarding prompts or credentials to a different origin.
- **Headless:** `LokalBot --agent "<prompt>"` runs one agent turn from the terminal (see Headless flags). It auto-approves file changes and, when the model runs on this Mac, read-only library lookups like every task, but safely declines other shell and external-read requests because no person is present to review them.

## Live Radar and Follow-through

Built during the Meta Global AI Developer Hackathon on top of v0.11.4; see [HACKATHON.md](HACKATHON.md). Live Radar, with its screen answers and live answers, and Follow-through have since moved from Meta's models to the Think model. Only fast live text still uses Meta's.

- **Live Radar's model:** `MeetingRadar` gets a Think engine per request from `ThinkExecution.makeTextEngine` (priority `.interactive`), so the backend, its origin approval, and the remote gate are Think's own. `ThinkChat` (`LokalBot/Engines/ThinkChat.swift`) turns the radar's chat messages into what a `TextEngine` takes: a pass is one schema-held reply (`structuredReply`, `MeetingRadar.passOptions`); a live-answer turn is one JSON tool call `{"call": {"tool": …, "arguments": …}}` held to a schema built from the function definitions (`toolCall`, `MeetingRadar.answerOptions`), with the tools described in the system prompt and earlier calls and results passed as context, as Ask's loop does. A reply that is not a call is asked for once more. The engines report no token use, so passes on Think carry no cost. Live Radar is offered only with `liveRadarEnabled` (off by default; settings saved before the switch existed default it to whether `https://api.meta.ai` was approved). In the UI-test host with `LOKALBOT_MUSE_UI_TEST` set, the radar keeps Meta's wire format (`MuseUITestTransport.radarCall`/`answerCall`) so the hosted film's scripted and live replies still apply.
- **Meta connection (fast live text; the film and the replays):** `MetaModelAPI` (`LokalBot/Engines/MetaModelAPI.swift`) holds Meta's OpenAI-compatible endpoint, the standard Muse models and prices, and `MuseChatClient`, a small `/chat/completions` client with function tools, strict JSON schema, `reasoning_effort`, and token use. In the app only fast live text reaches Meta; `MuseChatClient` serves the hosted film and the replay harnesses, and its reply and message shapes are what `ThinkChat` hands the radar and Follow-through loops. Requests share the origin's `RemoteInferenceGate` and the same-origin redirect rule. The key is the Keychain item `meta-model-api-key` (`lokalbot-cli secret set meta-model-api`), falling back to Think's key when Think points at `api.meta.ai`. Sending also needs `https://api.meta.ai` in `approvedRemoteInferenceOrigins`, set from Settings → Meetings → Meta Muse. Contributor models are left out on purpose.
- **Live Radar:** `MeetingRadar` reads `LiveMeetingTranscriber.lines` through `RadarLineFeed`, keeps its own copy of every line, and runs a pass at most every 20 seconds (sooner after 10 new lines). `MeetingRadarAnalyzer` builds the request: the new lines (labelled `L1`, `L2`, … for the whole recording), up to 24 earlier lines, items already found, and up to six passages from earlier meetings that `LibraryRadarEvidenceSource` finds with local keyword and semantic search. The reply must match a strict schema; each item must quote a new line (exact after normalization, or 80% of its words), and a contradiction must cite a passage (`E#`) or an earlier line (`L#`) it was shown. Everything else is dropped and counted as rejected. Results are saved to `radar.json` (`MeetingRadarRecord`) after each pass, with timing per pass (and tokens and cost where the model reports them). The pane sits between the live transcript and notes; the finished meeting's page shows a Live Radar section with Follow Through on the person's own commitments.
- **Fast live text:** with `museLiveTextEnabled` (off by default) and the api.meta.ai approval, `LiveMeetingTranscriber` runs `MuseLiveTextTrack` (`LokalBot/Services/MeetingRadar/MuseLiveText.swift`) for each tee file instead of chunked local ASR. Each track opens a realtime session (`wss://api.meta.ai/v1/asr/realtime`, `ENDPOINTING` mode, 16 kHz PCM; the key goes in the handshake frame), streams the growing CAF in 100 ms frames, and turns `speechComplete` into a `Line` timed from its `speechStart`, with the in-progress turn as `partials`. `MuseLiveTextPacer` starts a session at most three seconds behind the live edge and pads a stalled track with silence, because the server closes streams that fall below real time. A session that ran 30 s or more reconnects at once (the server caps sessions at 60 minutes); one that fails sooner backs off like a local chunk. Speakers stay per track. The radar sees `deliversTurns` and passes after each turn, at most every 3 s (`MeetingRadar.Timing.turnInterval`).
- **Turn-by-turn live text:** with `turnByTurnLiveTextEnabled` (off by default; Muse's fast live text takes precedence), `LiveMeetingTranscriber.runTurns` replaces the 4 to 12 second windows. Every 100 ms it reads the whole 256 ms chunks each tee file gained (`LiveMeetingAudioPreparationWorker.readChunks`), asks `SpeechActivity.liveProbability` for each chunk's speech probability, and feeds it to that track's `LiveTurnCutter`: a turn closes after two quiet chunks, after one once it is 4 s long, or at 15 s at the quietest point of its last 1.5 s. Closed turns wait in `pendingTurns` and are transcribed one at a time with the Transcribe model, each as its own file (`prepareSpan`); a failed one is retried with the windows' backoff and survives a pause. Between turns, while the last decode took 0.25 s or less and the model is on this Mac, the open turn is transcribed again every 2 s of audio and shown as a `partials` line, as Muse's are. `deliversTurns` is true, so the radar passes after each turn. Cursors, the cutter and the speech-detection state live in the track state, so pause and retry continue where they stopped. [Benchmarks/LiveTurns](Benchmarks/LiveTurns/README.md) has the measurements and the opt-in replay tests.
- **Floating panel:** `LiveRadarPanelController` (`LokalBot/Views/LiveRadarFloatingPanel.swift`) owns a borderless, non-activating `NSPanel` at `.floating` level (`canJoinAllSpaces`, `fullScreenAuxiliary`) hosting `LiveRadarPanelView`: the header with counts, `MeetingRadar.spotlightID` (the newest item, or the question that just got a screen answer) as a large `RadarCard`, the rest as rows, and the last transcript lines. `AppState` shows it when a recording starts with Live Radar on (`liveRadarEnabled` and `liveRadarPanelEnabled`) and from `startLiveRadar(for:)`, and hides it when the recording stops. `sharingType` is `.none` unless `liveRadarPanelHiddenFromCapture` is off (always `.readOnly` in the UI-test host, so the film can see it). Its top-left corner is kept in `UserDefaults` (`liveRadarPanelOrigin`).
- **Screen answers:** with `museScreenAnswersEnabled` (off by default), each question a pass adds starts `MeetingRadar.answerFromScreen` beside the passes. `LibraryRadarScreenSource` runs `ActivityStore.searchOCR` (OR'd terms, captures before now, not LokalBot's windows) and decrypts each hit; `RadarScreenAnswers.crop` runs Vision `.accurate` text recognition on the decrypted image and keeps a band around the best-matching lines, as wide as the text in it (at most half the screen tall, JPEG, at most 1,600 px wide) plus that band's text in reading order. The text of up to three crops goes to the Think model (`RadarScreenAnswers.textMessages`) with a strict `{answer, image, quote}` schema; `RadarScreenAnswers.answer` keeps the reply only when the quote is in that crop's text. The hosted film and the replay send the crops themselves as `image_url` parts (`RadarScreenAnswers.messages`). The crop is saved as `radar-answers/<item>.jpg` and the answer as `RadarItem.screenAnswer`; the request is recorded in `MeetingRadarRecord.screenAnswerRequests`.
- **Live answers:** with `liveAnswersEnabled` (off by default), each question a pass adds also starts `MeetingRadar.answerLive`, which runs `LiveAnswerSession` (`LokalBot/Services/MeetingRadar/LiveAnswers.swift`) on the Think model (at most 6 model turns and 60 s). Memory comes first: `AppLiveAnswerEnvironment` puts the "Where it stands" notes of up to two tracked projects that share words with the question, active actions from the last 30 days, `PersonalContextBuilder` claims (when `askMemoryEnabled`), and work memory in the prompt as `[C1]`, `[C2]`, …. Then the model may call Ask's `search_meetings`, `get_meeting`, `get_action_items`, and `search_screen`, and `LiveAnswerTools` (`LiveAnswerTools.swift`) over `liveAnswerFolders`: `search_documents` (Spotlight with `mdfind -onlyin`, else file names ranked by the query's words, since Spotlight skips `~/Library`), `read_document` (PDFKit, `textutil`, and a small `.xlsx` reader, cut to the lines around the query), and in git repositories `search_code` (`git grep -F`), `read_file` (tracked files only), `recent_commits`, and `github` (`gh pr`/`gh issue`). Hidden paths, `node_modules`, and secret-looking names are never read, and commands time out after 8 s. Each tool result is labelled `[R#]`, and the `answer` tool must cite `C#`/`R#` ids with exact words; `LiveAnswerSession.ground` keeps a source only when its quote is in what it names (`RadarScreenAnswers.quoteIsOnScreen`) and titles it by the matching line (`path:line` with a GitHub permalink at the checked-out commit, a commit, `#123`). The answer is `RadarItem.answer` (`RadarAnswer`), the card shows `MeetingRadar.answerSteps` while it works, and the request is recorded in `MeetingRadarRecord.answerRequests`.
- **Follow-through:** `FollowThroughSession` runs a tool loop on the Think model (at most 10 model turns): `AppState.startFollowThrough` asks `ThinkExecution.makeTextEngine` for an engine at each turn (priority `.interactive`), so the backend, its origin approval, and the remote gate are Think's own, and `ThinkChat.toolCall` turns the turn into one JSON tool call (`FollowThroughSession.turnOptions`), as for live answers. The engines report no token use, so a run carries no cost. In the UI-test host with `LOKALBOT_MUSE_UI_TEST` set, it keeps Meta's wire format (`MuseUITestTransport.followThroughCall`) for the hosted film. Read tools are Ask's `search_meetings`, `get_meeting`, and `get_action_items`; screen search is excluded because it has its own grant. Proposal tools (`draft_email`, `propose_meeting`, `hand_off_to_coding_agent`, `mark_action_done`) only create a `FollowThroughProposal`; the loop waits for the person to approve, edit, or decline it in `FollowThroughSheet`, and returns what happened to the model. `AppFollowThroughEnvironment` carries out approved steps: a `mailto:` draft (also saved as the meeting's `follow-up-draft.json`), an `.ics` invitation opened in Calendar, a prompt filled into Claude Code or Codex through `ActionAgentHandoff`, or Mark Done. Names are resolved to calendar addresses on this Mac and addresses never go into a model message. Menus on action rows offer **Follow Through…**.
- **Replays:** `--radar-replay` and `--follow-through-replay` run the same request, grounding, and loop code against a fixture on Meta's models, with `META_API_KEY` from the environment; see [Benchmarks/MuseRadar](Benchmarks/MuseRadar/README.md).

## Screen context, OCR & privacy

- **Capture:** fresh settings select activity only; visible text and pixels require explicit opt-in and the applicable macOS grants. A bounded, single-flight Accessibility reader collects visible text first; Vision (`VNRecognizeTextRequest`, on-device) runs only when that text is too thin. Coarse triggers include app/window changes, clicks, typing pauses, settled scrolling, and pasteboard-generation changes, plus an idle-active fallback. The trigger monitor never reads raw keys, pointer positions, scroll deltas, or clipboard contents. Automatic work has a 20-second cooldown; byte-identical frames and unchanged text are skipped. Visual mode uses ScreenCaptureKit, downscales to ≤1500 px, encodes HEIC, and groups similar scenes with a 64-bit perceptual dHash.
- **Contextual privacy:** capture skips idle/lock/pause states, excluded apps and domains, and focused secure fields; private and incognito windows are captured like any other window. URL metadata drops credentials, query, and fragment; document metadata keeps only the filename. Deterministic rules redact captured text before persistence: credentials, including prefixed names (`DB_PASSWORD=`, `GITHUB_TOKEN:`), common provider token formats, and URL passwords, plus payment card numbers (issuer prefix and Luhn) and IBANs (mod 97). If either accessible text or OCR detects a credential, the redacted text remains useful but the pixel payload is never written.
- **Meetings:** visual context during recording is a separate opt-in. It is throttled to at most one automatic moment per minute and rows carry the active meeting id. Manual capture remains available.
- **Encryption & retention:** each retained visual is AES-GCM sealed with a per-install Keychain key. Pixels auto-delete after N days (default 14), and captured text follows the same retention unless you opt into keeping it forever. Saved moments retain their encrypted pixels, text, and semantic vector until unsaved or explicitly deleted. Accessibility-only and retention-pruned moments remain represented as text context rather than fake thumbnails.
- **Exclusions:** the comma-separated app list is preseeded with password managers, and the Passwords app, Keychain Access, 1Password, Bitwarden, and KeePassXC are skipped by bundle identifier whatever their name in the user's language or the list. A rule matches the app's display name; a rule with a dot also matches that bundle identifier and those beneath it, and **Choose App…** stores the bundle identifier; excluded time logs as "Private" with no title or context. Domain/URL-prefix rules apply to both text and pixels.

## Safe local routines

- **Curated jobs:** post-meeting follow-up, daily stand-up, weekly work log, unfinished-action rollup, and local journal. Each renderer has a fixed local read scope and accepts no arbitrary prompt, shell command, or network action.
- **Scheduling:** event-driven follow-ups run after processing; daily and weekly jobs catch up after wake. Meeting recording, dictation, cotyping generation, and the meeting pipeline take priority. Fixed calendar scopes and fingerprints of prepared output make corrections, completion, deletion, and reverted edits new durable revisions. Unchanged successful or failed revisions are terminal across relaunch; invalidation cancels stale work. Preparation and writing each have a 30-second bound.
- **Writes:** Markdown goes only under a user-selected destination with `0700` folders and `0600` files. Routines and daily exports share hash-sidecar ownership checks: unchanged output is idempotent, changed generated output is replaced only while its stored hash matches, and user edits or unrelated files are preserved. Legacy files without a sidecar can be adopted only when their bytes already equal the new output. Deterministic secret redaction is applied again before writing.

## Email (read-only)

- **Accounts:** Settings → **Email** connects one or more Gmail accounts (`LokalBot/Services/Email/`), after a notice that says what is read. Sign-in uses LokalBot's own Google client, an "iOS"-type client with no secret (`GmailOAuth.builtInClientID`), in Apple's `ASWebAuthenticationSession` sheet, which returns only to the client's `com.googleusercontent.apps.<id>` scheme (`GoogleSignInSheet`). It uses PKCE and asks only for `gmail.readonly`. Under **Use your own Google OAuth client**, a person can import a Desktop-app client JSON (Keychain), which signs in through the browser and a `127.0.0.1` loopback redirect instead. Each account's tokens record the client that issued them, so refreshes use that client. `GmailAuthorizer` caches one Keychain token set per account and serializes refreshes; Disconnect deletes locally, then revokes. Nothing touches the Keychain until an account is connected. Google Cloud setup and verification: [Docs/google-oauth-verification.md](Docs/google-oauth-verification.md).
- **What is read:** `EmailScope` decides from headers alone whether a thread is downloaded: the person wrote in it (Gmail's SENT label; a `From` header with their address proves nothing), or a calendar attendee from the last 90 or next 14 days takes part and the mail isn't bulk (Gmail's non-Primary tabs, `List-Unsubscribe`/`List-Id`, `Precedence`, `Auto-Submitted`, no-reply senders). Spam, Trash and Drafts are never kept, attachments keep only name, type and size, and messages older than 90 days age out. HTML bodies are tokenized to text without loading anything (`EmailText.plainText(fromHTML:)`); `<blockquote>` history keeps a `> ` prefix.
- **Sync:** `GmailSyncer` scans the window on the first pass (`in:sent` plus attendee searches), then replays Gmail's history from the saved `historyId`, rechecking only the threads it names (reading, starring and archiving are ignored), and searches once for any attendee added since; only searches that ran to the end mark people as searched. Attendees are remembered for 90 days after they were last on the calendar, so a calendar that is briefly unreadable deletes nothing and searches nothing. An expired history ID rescans the window. The cursor is saved only after the threads it covers are stored; a thread Gmail fails to return is kept as it was and retried next pass, while more than a few failures at once end the pass. Pruning drops a thread whose remaining messages no longer qualify. `GmailClient` sends only `GET` requests to `gmail.googleapis.com`, refreshes the token once after a 401, and backs off on 429, 5xx and per-user rate limits. `EmailController` checks each account once the library has loaded after launch, after 06:00 each day, 30 minutes before a meeting with attendees, every three hours, and on **Check Now**, never twice within 15 minutes; it doesn't run in headless commands or the UI test host. Tokens are read from the Keychain once per launch, and a Keychain read failure is reported, never treated as a sign-out. It refuses to save over an account list it couldn't read, and Disconnect removes the account, its mail and its tokens before asking Google to revoke.
- **Meeting briefs:** the only reader. `UpcomingMeetingPreparationModel` takes `EmailController.mailbox()` (reused until `mailRevision` or the event changes), and `EmailMeetingContext` picks up to five stored threads whose participants include the event's attendee addresses. Your own addresses are excluded, and display names never match. Threads are ranked by attendees involved, recency, an unanswered question to you, and subject overlap. Each becomes a "From email" row on the Today card, opening the thread in Gmail with `authuser`, plus a prompt block of the last three non-bulk messages tagged "you" or the sender. That text has quoted history and signatures stripped (`EmailText.conversationText`) and secrets redacted (`ScreenContextPrivacy.redact`), and it is capped at 3,000 characters. The brief's system prompt forbids following instructions in mail, and generation already refuses remote models. Earlier meetings now also match attendees by address.
- **Storage:** `email/accounts.json.enc` and `email/<account-id>/threads/<thread-id>.json.enc`, AES-GCM sealed with the `email-key` Keychain key, `0600` files in `0700` folders. Mail never enters `lokalbotv3.sqlite`, the embeddings, Dream reports or exports ([plan](Docs/email-access-plan-2026-10-26.md)).

## Meeting note export

- **Notes:** Settings → Meetings → **Meeting note export** writes one note per finished meeting that has a summary, or a transcript when transcripts are included, to a folder the person picks: plain Markdown, Obsidian (YAML properties, `[[links]]` for people and projects), or Logseq OG (`key:: value` properties, `TODO`/`DONE` actions). `MeetingNoteExportService` renders `summary.md` with its action list replaced by the outcome projection's, so corrections apply and completed actions are checked off; people come from `PeopleDirectory` and tracked projects are matched with `ProjectLinks` word matching, as on the People and Projects pages. Detected credentials are redacted.
- **Ownership:** a note is named `YYYY-MM-DD Title (shortid).md` when first written and found again by its short id, so renaming a meeting keeps the note's name and the links to it. The daily export's hash sidecar decides refreshes. An edited note, or a sidecar whose note is gone (deleted, or moved elsewhere in the vault), belongs to the person, and that meeting is not written again. Deleting a meeting leaves its note.
- **Scheduling:** `MeetingNoteExportScheduler` runs a pass when configured, after `primaryEvidenceDidChange`, and after People or Projects curation changes, checking at most once a minute and never while the pipeline has work. Each pass fingerprints every meeting folder's files with the meeting's people and the tracked-project names, and renders only meetings whose fingerprint changed since the last pass; a failed pass is retried after 15 minutes.

### Fun-ASR-Nano local transcription

Choose **Settings → Models → Transcribe → Fun-ASR-Nano-2512 → Choose model
folder…**, select an extracted model directory, then choose **Use model**.
LokalBot checks the files and loads a short synthetic input before activating
the selection. A failed or cancelled load leaves the previous model active.

This uses the bundled sherpa-onnx CPU runtime and its
[Fun-ASR-Nano-2512 ONNX exports](https://k2-fsa.github.io/sherpa/onnx/funasr-nano/pretrained.html),
not the original Hugging Face/ModelScope PyTorch checkpoint. Supported layouts:

| Export | Encoder / embedding | Decoder | Extra weights |
| --- | --- | --- | --- |
| int8 | `encoder_adaptor.int8.onnx`, `embedding.int8.onnx` | `llm.int8.onnx` | — |
| fp16 | Same int8 encoder and embedding | `llm.fp16.onnx` | — |
| fp32 | `encoder_adaptor.onnx`, `embedding.onnx` | `llm.fp32.onnx` | `llm.fp32.data` |

All layouts need `Qwen3-0.6B/tokenizer.json`, `vocab.json`, and `merges.txt`.
An inline `llm.onnx` decoder is also accepted. Actual graph compatibility is
checked by the runtime; empty files, Git LFS pointers, missing tokenizer files,
and missing fp32 external weights are rejected before loading.

The selected path is saved as `funASRNanoModelDirectory`. Files are used in
place, including local cache symlinks; the app never imports, overwrites, or
deletes this directory. **Clear selection** in the picker is saved with the
**Clear selection** button at the bottom; **Cancel** keeps the saved path.
Undo validates the previous folder before restoring it. Removing the model in
**Downloaded** also only clears the saved path. Moving the folder requires selecting it again. No Fun-ASR model
download or remote inference occurs. The existing shared Silero VAD may still
download its small pinned model on first use, as with other transcription engines.
Speech is decoded in at most 20-second regions with span/coarse timestamps;
this is not streaming or word-aligned transcription. Chinese, English, and
Japanese hints are supported; automatic detection is used for other selections.

`FunASRNanoModelTests`, `FunASRNanoSelectionTests`, and the FunASR cases in
`ModelRolesTests` cover directory validation, settings persistence, selection
undo, readiness invalidation, file ownership, and preparation cancellation.
`FunASRNanoRuntimeTests` checks subprocess results and offers an opt-in real
model check using `LOKALBOT_FUNASR_TEST_MODEL_DIR` and `LOKALBOT_FUNASR_TEST_WAV`
(public or synthetic audio only). Prefix these variables with `TEST_RUNNER_`
when running through `xcodebuild`.

The app language menu is on the first step only.

- **Choose:** Meeting notes is a switch over `autoRecordMode` (off is `.manual`; the draft remembers the automatic or ask choice behind it), Your workday is `trackingEnabled` with the capture mode beside it, and Coding agent sessions is the master switch.
- **Allow access:** `OnboardingAccess` lists only what the draft needs (the microphone always, Accessibility for the workday, Screen Recording for screenshots) and gives each row its state from `PermissionManager`: needed, waiting after System Settings was opened, allowed, allowed after a restart (granted since `grantedAtLaunch`), or turned off (`turnedOff`, a refused microphone). **Restart now** saves an `OnboardingResumeState` (step, draft, the settings the draft started from, the two download options) through `OnboardingResumeStore` and relaunches; the window keeps that state current while it is open, since macOS can also ask to quit after a Screen Recording grant. At launch `OnboardingLaunch.decision` reopens an unfinished setup that has saved state even when the microphone is already granted, and a finished one only after its own Restart now. Saved state is ignored once the settings no longer match the ones the draft started from, and `markSetupFinished` clears it.
- **Download:** `OnboardingDownloadPlan` turns the `ModelRoles` statuses into rows with each model's job, name and size (`ModelSettingsPresentation.estimatedTranscriptionBytes` and the catalog's byte counts), the total still to fetch, and the free space from the readiness snapshot. Nothing downloads until the button that names the size is pressed. While it runs, the plan counts only the models that were missing when it began; `DownloadTimeEstimator` gives minutes left from the last 30 seconds of progress once it has watched for 5, and the amount alone before that. A failed model reads Stopped with Retry, which calls `startCoreModelDownloads` again. The sample-meeting option sets `AppState.sampleMeetingWaitsForModels`; `openWaitingSampleMeeting` adds the sample when the models become ready, also after the window has closed, until LokalBot quits.

## Agent CLI & MCP

`lokalbot-cli` (ArgumentParser, embedded in `Contents/Helpers/`) gives coding agents read-only access to the meeting library via `list` / `get` / `search` / `actions` / `people` / `path`, to shared Personal Context via `personal-context`, and to the Files index via `search-files`, plus `ask` and `reply`, which answer a question or draft a reply to a message with the app's local model through the same `AskLibraryEngine` path as `ask_library` (the Raycast extension in `Distribution/raycast/` uses them), and to app settings and status via `config` / `status` / `open`. `actions` and `people` share the app's outcome projection, thread clustering, due-date resolution, and People rules (the CLI target compiles those model files). JSON by default, `--table` for humans. `list --include summary` (MCP: `list_meetings` with `include`) adds several meetings' summaries in one call; they share a 20,000-character budget (`SessionFormatter.listSummaryBudget`), split so short summaries stay whole, and a cut one carries `summary_truncated`. Settings → External Agents → Agent CLI (or `lokalbot-cli install-skill`) symlinks the binary to `~/.local/bin/lokalbot-cli` and the bundled skill to `~/.agents/skills/lokalbot-cli/`.

The same binary is an **MCP server**: `lokalbot-cli mcp` speaks MCP over stdio. Meeting tools are `list_meetings` / `get_meeting` / `search_meetings` / `ask_library` / `get_action_items` / `list_people` / `get_person`; people tools return names only, never attendee addresses. Independently gated screen tools are `search_screen` / `get_timeline` / `get_recent_activity` / `get_app_usage` / `get_screenshot_detail`; they use a query-only SQLite connection and return captured text/metadata, never decrypted pixels or file paths. `get_personal_context` (CLI: `personal-context`) returns Personal Context items the user shared, ranked for the agent's task. `search_agent_notes` (CLI: `search-notes <query> [--agent] [--limit] [--table]`) searches the saved coding-agent notes by words through `AgentNotesIndex`, with the app closed. `search_files` (CLI: `search-files <query> [--kind screenshot|image|pdf|doc|audio|video …] [--after YYYY-MM-DD] [--before YYYY-MM-DD] [--limit N]`, `FilesSearchTool` in `CLISupport/FilesAccess.swift`) is word search over the Files index: DigUp's keyword search of the text Files extracted from documents, PDF pages, screenshots and pictures, plus file names, opened from `files-index.noindex` without vectors, so it works with the app closed. Hits outside the folders in `control/files-access.json`, or no longer on disk, are dropped; each result has the path, kind, page or seconds, modified and EXIF capture dates, size, excerpt and the matched passage (cut at 1,500 characters). Recordings and video match only by name. Search by meaning stays in Ask, because it needs the app's embedding model. It returns `files_access_disabled` without the grant and `files_unavailable` while Files is off, has no folder, or has no index yet. `get_briefing` (CLI: `brief`, listed first, and named in the `initialize` result's `instructions`) is the start-of-session overview built by `Briefing` in CLISupport; `brief` renders it with `Briefing.Vocabulary.cli`, naming `lokalbot-cli` commands where `get_briefing` names MCP tools: a capability index that is shown even with every grant off (for Files it says only whether the grant is on and how many folders it covers), then shared Personal Context items, the user's open action items, work-memory projects and goals (each source kind needs its grant, unattributed entries are skipped, and everything waits while `.dream-revocation-pending.json` exists), coding-agent sessions from `coding_agent_bursts`, and a review timeline: days from `dreams/*.json`, then week and month lines from `dreams/rollups/`, clamped to the screen profile and capped at 12,000 characters. `DreamRollupService` writes those lines after each overnight review (at most three, at most once in 20 hours via `dreams/rollups/.last-generation`, and only while agents may read all retained screen history, the only scope whose briefing shows them); each records a SHA-256 stamp of its reviews' days and `generatedAt`, so a deleted or regenerated review makes it stale. Stale lines are never shown, and `DreamStore.invalidateReport` deletes them. The server reads stdin with `read(2)`, so a client that keeps stdin open gets each reply immediately. The screen marker stores one of three profiles: today, rolling seven days, or all retained history; every query is clamped and out-of-scope detail ids appear missing. LokalBot does not upload library content, but an external MCP client may transmit tool inputs and results under its own privacy terms.

All agent surfaces are **off by default**. Meeting tools require `control/agent-access-enabled`; screen-memory tools require the separate JSON `control/screen-memory-access-enabled` marker; personal context requires `control/personal-context-access-enabled` plus the app-written `control/personal-context.json`; `search_files` requires `control/files-access-enabled` plus `control/files-access.json`, the chosen folders, which `FilesAccessManager` writes only while the grant is on and Files is on with a folder; `search_agent_notes` requires `control/agent-notes-access-enabled` and finds notes only while `agent-notes.sqlite` exists; settings commands require `control/settings-control-enabled`. No marker grants another capability, and Agent Mode capabilities don't grant personal context or files. In the Mac app, Settings → External Agents shows the four read grants as one switch, **Allow external agents to read your LokalBot data**, with a box per kind (Meetings, Screen memory, What I shared about myself, Files). `AgentReadAccess` only writes and removes the per-kind markers: turning the switch on grants the ticked kinds (Meetings alone the first time), and turning it off removes every read marker and saves the boxes and the screen scope to `control/agent-read-choices.json`. The switch is on exactly while some kind is granted, so grants from the old per-kind toggles or from agent setup show as they are, nothing widens on upgrade, and Files starts off. The last ticked box can't be unticked. Access-off messages name that path (`AgentReadAccessCopy`), and `open settings filesAccess` (like `agentAccess`, `screenMemoryAccess`, `personalContextAccess`, and `settingsControlAccess`) opens Settings at that box. Settings access stays a separate switch. Empty markers written by older builds retain their prior unscoped authorization until the user chooses a profile; newly enabled access defaults to seven days.

**Settings and status.** `lokalbot-cli config schema|describe|search` read `SettingRegistry` (`CLISupport/SettingRegistry.swift`) without the app: every persisted `AppSettings` key with its Settings category, type, consent tier, and choice tokens (enums that store display strings or key codes map to stable tokens). `config list|get`, `status`, and `open settings [key]` ask the running app over a Unix socket, one JSON request per connection (`AppControlProtocol`, `AppControlServer`, `AppControlHandler`). The socket is `control/app.sock` (0600, in the 0700 control folder), or a per-user `/tmp` name when the root path exceeds `sun_path`; it exists only while `control/settings-control-enabled` is on, and the app checks the peer's uid and re-checks the marker on every request. When no app answers and none holds the library's `.instance.lock`, the CLI launches its own enclosing bundle with `open -g -j <app> --args --lokalbot-background-launch`; menu-bar-only installs then start silently, like a login launch. `SettingRegistryTests` fails when a stored key has no spec or a choice drifts from its enum. `config set|reset|import` send `settings.set`: `SettingChange.swift` parses typed values, maps tokens to stored values, and classifies each change as preference, narrowing, widening, or read-only; `SettingsChangeApplier` decodes the result with the real decoder (a rejected or adjusted value is an `invalid_value` error) and applies the couplings Settings enforces (tracking and capture mode, the dreaming start day). Requests apply all or nothing. A request with a widening change goes, whole, to `SettingsApprovals` and returns `needs_approval` with the request (`id`, `changes`, any retention review) in `details`; the app posts a notification through `RecordingNotifier` (or opens the `settings-approval` window when notifications are off), the menu bar's status block lists it with Review and its icon carries a dot, and the window's card applies it through `AppState.applyApprovedSettings`, which re-plans against current settings, applies a shorter retention policy only through the review the card showed, and asks for the permissions the Settings controls would. `settings.request` reports `pending`, `approved`, `denied`, or `expired` (5 minutes); the CLI's `--wait` polls it and exits 0, 3, 4, or 5. `secret.set` queues an API key the same way (`AppSecret`, held in memory until answered, written through `AgentSecretStore`), and `secret.clear` removes one directly. The couplings and permission prompts the Settings controls use live in `AppState+AgentSettings.swift` (`changeSettings`, `coupledSettings`, `requestPermissions(forChangeFrom:to:)`, `applyRetentionReview`), shared by the controls, the socket, and Undo. `AgentSettingsChanges` appends each applied change, with the caller (the peer pid from `LOCAL_PEERPID` and its nearest non-shell ancestor), to `diagnostics/settings-changes.jsonl` and backs the Undo list in Privacy. `status` also reports model readiness, onboarding, and waiting approvals. Agent-led setup ([AGENT_SETUP.md](AGENT_SETUP.md)): `setup start` is the one request that needs no grant. The CLI writes `control/setup-request.json` (`AgentSetup.Request`, five minutes, 0600), opens its own bundle with `--lokalbot-agent-setup` or posts the `me.dotenv.LokalBot.agent-setup-requested` distributed notification to a running copy, and polls `control/setup-answer.json`. `AgentSetupRequests` shows the request in the `agent-setup` window (instead of the onboarding wizard on a new install), and only Allow writes the markers. `setup start --meeting-library`, `--screen-memory`, and `--files` add a box each to that window (Let agents read your meetings, Let agents read screen memory, Let agents search your files), off unless the person ticks it. `setup.plan` returns `SetupPlan.keys` with current values and the preset `suggestedPreset` picks for this Mac's memory; the CLI's `setup apply` applies preferences directly and sends consent changes to one approval card. `models.*`, `permissions.*` (the table behind Memory Health), `app.launchAtLogin`, `app.restart`, `setup.finish`, and `doctor` live in `AppControlHandler+Setup.swift`; prompts, launch at login, and restarts are refused outside the interactive app. See [the design](Docs/cli-configuration-design-2026-10-17.md).

See [`.agents/skills/lokalbot-cli/SKILL.md`](.agents/skills/lokalbot-cli/SKILL.md).

## Testing

- **Unit** (`LokalBotTests`, in-process):
  ```bash
  xcodebuild -project LokalBot.xcodeproj -scheme LokalBot -destination 'platform=macOS' test
  ```
  Pure-logic coverage — prompt sanitizers, search ranker, model fit, transcript merging, settings codecs, data migration, and the chat agent (tool-call parsing for JSON **and** native function-call forms, the ReAct loop, observation formatters).
  Select an affected class or method with `-only-testing:LokalBotTests/CotypingCoordinatorTests` (replace the class with the relevant test).
  Unit tests never read the checkout or `~/Documents`, because macOS asks each freshly built test host for Documents access. `project.yml` copies the repository files tests check into the test bundle, `Scripts/unit-tests.sh` builds outside the checkout (`--derived-data-path` prints where; `LOKALBOT_DERIVED_DATA` overrides it), and real-model cotyping tests read `LOKALBOT_COTYPING_TEST_MODEL` instead of `Vendor/llama-models`.
  A skipped test is not a passed one. `Scripts/unit-tests.sh` and the hosted unit job run `Scripts/ci/unit-skips.py` on the result: a run fails when a test skips that `Scripts/ci/unit-skips.json` does not name. That file lists every opt-in test with what it needs (a model folder, a key, a private fixture) and when to run it; the hosted job also fails when a listed test runs or no longer exists, so remove a test from the list in the change that makes it run.
  Unit tests never download models. Their settings turn semantic search on, so `AppState` gives its embedding index `EmbeddingIndex.unavailableEmbedder`; any other test that reaches the real embedder has the model download refused (`UITestRuntime.refuseDownloadInUnitTests`), and the bundle's principal class, `LokalBotTestObservation`, fails that test. Pass `embedder:` to `EmbeddingIndex` when a test needs vectors. `EmbeddingIndexIntegrationTests` uses the real model from its fixture library's `models/` folder.
- **Qwen upgrade parity:** `QwenASREngineTests/testCachedModelTranscriptionMatchesReferenceWhenProvided` uses cached weights from `LOKALBOT_QWEN_TEST_MODEL_DIR` and a `LOKALBOT_QWEN_TEST_REFERENCE` JSON array of `{id, audio, language, text}` records. Recorded notes answers quote the golden wording, so the real-ASR run checks the day's word error rate against the golden transcripts (case, punctuation, hyphens, and split or joined compounds ignored; at most 10% across the day's meetings, so one misheard word in a short meeting cannot decide the run) and that the design review's notes finish, instead of the quoted owner. A failed nightly run uploads its library as the `day-in-the-life-real` artifact.
- **UI background shard:** `BackgroundFlowUITests` runs the UI Test Host with its background work on (`LOKALBOT_UI_TEST_BACKGROUND=1`, a replayed trace, file audio, golden transcripts, and the model stub). `Scripts/ci/ui-shards.py` gives it its own `background` shard, and the aggregate XCUITest gate requires it. Hosted CI only, like every UI test.
- **Upgrade fixtures:** the `Upgrade fixtures` workflow seeds a library with each release's own seed script, opens it with that release's signed build on a clean hosted Mac, and uploads the library, defaults, and synthetic test keys. Each stable release run builds its own fixture once the DMG is published; the next release candidate adds it with `Scripts/upgrade-fixtures/add.sh <version>` (RELEASING.md step 0). The committed folders in `LokalBotTests/Fixtures/upgrade/` are the list of fixture versions: a dispatch without versions rebuilds them all, and a pull request that changes the generator rebuilds the newest.
- **Nightly:** `.github/workflows/nightly.yml` compares pinned models with their GitHub releases (`Scripts/ci/check-model-pins.py`), and runs model drift, the real-Parakeet workday, and scale checks (a 180-day library, a digest while activity is written, two copies on one library). It never blocks a PR; failures open or update an issue.
- **Health checks:** Debug builds evaluate yesterday at 09:00 (and on the next launch if that was missed) and post a notification that opens the report on failure. `LokalBot --health` runs the same checks on demand. Reports are written to `diagnostics/health/YYYY-MM-DD.{json,md}` in the library. Settings → Diagnostics → System has **Run Health Check Now** and **Export Diagnostics…**.

Rooted at the bundle id (not "LokalBot") so it never collides with another app's `Application Support/LokalBot` on the default case-insensitive filesystem.

Legacy migration never replaces an existing current database, including an empty one. A missing database is imported through a WAL-aware SQLite snapshot and atomic no-replace installation; concurrent creation wins safely. Conflicting legacy data and recovery snapshots remain available for explicit reconciliation. Dev, UI-test, and fixture launches skip legacy migration.
